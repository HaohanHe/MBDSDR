### 1.3 构建体系

- `CMakeLists.txt` 要求 **CMake ≥ 3.22.0**。
- 同一份源码支持 **Qt 5 与 Qt 6**：`BUILD_WITH_QT6` 默认 `FALSE`（注释为 experimental）；Qt5 最低 **5.15.2**，Qt6 最低 **6.4.0**。
- 组件开关：`WITH_GUI`、`WITH_DESKTOP`、`WITH_PYTHON`、`WITH_BINDINGS`、`WITH_3D`、`WITH_SERVER`、`WITH_SERVER_PLUGINS` 等；依赖关系在顶层做 `FATAL_ERROR` 校验（例如 `WITH_DESKTOP` 必须 `WITH_GUI`，Server 插件必须有 Python 绑定）。
- 产物形态：`core` → 静态/动态库；`gui` → 库；`app` → 桌面可执行；`server` → `qgis_mapserv.fcgi`；`python` → `_core`/`_gui` 绑定模块。
- 依赖查找优先用自带 `cmake/Find*.cmake`，再回落到系统包；`PREFER_INTERNAL_LIBS` 控制是否优先使用 `external/` 内置副本。
- 版本与路径写在 `cmake_templates/qgsconfig.h.in` 生成的头里，运行期由 `QgsApplication` 统一读取。

### 1.4 第三方依赖策略

三类：

1. **系统级 GIS 栈**：GDAL、PROJ、GEOS、SQLite、SpatiaLite、Postgres client、ODBC、EXIV2、LibZip、ZSTD、lcms2。由 `FindGDAL.cmake`、`FindProj.cmake`、`FindGEOS.cmake` 等查找。
2. **Qt 生态**：Qt Widgets、Qt Network、Qt SQL、Qt SVG、Qt Xml、Qt Concurrent、Qt3D（3D 可选）、QScintilla（代码编辑器）、Qwt/QwtPolar（绘图，`external/qwtpolar-1.1.1` 带内置副本）。
3. **必须随源码走的库**：`external/` 下 26 个，特点是上游不稳定、Windows 上难装、或需要打补丁（MDAL、PDAL wrench、PDF4QT、qspatialite、nmea、rtree）。

对我们的直接含义：QGIS 的「依赖重」不是因为用了 Qt，而是因为 GIS 栈本身（PROJ/GDAL/GEOS）体量大且 ABI 敏感；我们若只借「坐标变换/椭球量算」的一小块，需要确认能否只引 PROJ 而不引 GDAL/GEOS（见 10.1、10.2）。

### 1.5 界面框架

- Qt Widgets + `.ui` + 手写 `QgsXxx` 控件；`src/gui` 是可复用控件库，`src/app` 只做装配。
- 主题不是单纯 QSS：`QgsApplication::setThemeName()/themeName()` 管主题名，图标经 `QgsApplication::getThemeIcon()` 按主题解析，配色另有 `QPalette` 与 QSS 两条路径（详见第 8 章）。
- 可选 QtQuick 面：`src/quickgui`（移动/触控），与桌面 Widgets 面并存但独立。
- 可选 3D 面：`src/3d`，依赖 Qt3D；这是典型的「重且与我们无关」的部分（见第 11 章）。

### 1.6 扩展机制（概览）

三层，细节在第 7 章：

1. **C++ 插件**：`QgisPlugin` 接口（`src/plugins/qgisplugin.h`）+ `QgsPluginRegistry`（`src/app/qgspluginregistry.cpp`），编译成动态库放进 `plugins/`。
2. **Python 插件**：`python/utils.py` 的 `loadPlugin()/startPlugin()/unloadPlugin()`，以目录 + `metadata.txt` 为发现单元，可在运行期启停。
3. **内部注册表**：`QgsApplication` 上挂的一批 `QgsXxxRegistry`（渲染器、符号层、数据提供者、Processing 算法、定位器过滤器等），核心代码只面向注册表接口，不在 `switch` 里硬编码类型。

### 1.7 国际化与资源

- 翻译：`i18n/*.ts` 经 `lrelease` 编成 `.qm`；运行期由 `QgsApplication::setTranslation()/translation()` 触发 `installTranslators()`（`qgsapplication.cpp`），按 `qgis_<locale>`、`qt_<locale>`、`qtbase_<locale>` 三类各装一个 `QTranslator`，插件翻译另有加载路径。
- 资源：绝大多数不是 `.qrc` 编译进二进制，而是由 CMake 把 `resources/` 拷到构建/安装目录（`resources/data`、`themes`、`cpt-city`、`symbols`）；`.qrc` 只用于少量必须内嵌的资源（如 3D 纹理）。
- 主题目录约定：`resources/themes/<ThemeName>/`，主题内再分 `icons/`、`style.qss` 等（详见 8.3）。

## 2. 分层与依赖方向

**QGIS 的做法**

- 三层严格单向：`core` → 不依赖 GUI；`gui` → 依赖 `core`；`app` → 依赖 `gui + core`。`src/core/CMakeLists.txt` 的 `target_link_libraries(qgis_core ...)` 只出现 `GDAL::GDAL`、`GEOS::geos_c`、`PROJ::proj`、Qt 模块与内置库，没有任何 `qgis_gui`。
- 插件不拿主窗口具体类型，只拿接口 `QgisInterface`（`src/gui/qgisinterface.h`）。接口暴露的是能力而不是控件树：`mapCanvas()`、`messageBar()`、`addDockWidget()`、`addPluginToMenu()`、`activeLayer()`、`mainWindow()`。插件的 `initGui(QgisInterface*)` 只能看到这些。
- `QgsApplication` 继承 `QApplication`，是**服务容器**：`initQgis()`（`src/core/qgsapplication.cpp`）按固定顺序建好设置、翻译、任务管理器 `taskManager()`、消息日志 `messageLog()`、处理注册表 `processingRegistry()`、配色注册表 `colorSchemeRegistry()` 等；全局单例都从这里取，业务代码不自己 `new`。
- 具体主窗口是 `QgisApp`（`src/app/qgisapp.cpp`），它实现 `QgisInterface`（`src/app/qgisappinterface.cpp` 做转发），把「能力接口」与「窗口实现」分开。
- 可选产品面（`3d`、`server`、`quickgui`、`analysis`）各自成库，依赖 `core/gui`，不被 `core` 反向依赖。

**我们现在的做法**

- `desktop/` 没有等价的接口层：`MainWindow` 直接构造面板与 `QThread`（`desktop/main_window.py`），面板通过构造参数拿服务；`desktop/panel_registry.py` 只登记元数据，不约束面板能碰什么。
- `cpp/` 已经有类似边界：`cpp/src/ui/main_window.cpp` 把「UI-only settings」经由抽象 surface 交给 tool/engine 层，避免 UI 与底层逻辑直接耦合；但还没抽成 `QgisInterface` 那样的显式能力接口。
- 依赖方向本身是干净的：`mbdsdr_ai/` 不 import PySide6（`desktop/` 才 import），`cpp/src/dsp`、`cpp/src/radio` 不依赖 `cpp/src/ui`。

**差在哪**

1. 我们缺「插件可见能力面」：一旦要做第三方/内部扩展面板，只有 `PanelRegistry` 的元数据约束，没有编译期/运行期可检查的接口，面板很容易直接抓 `MainWindow` 的属性。
2. QGIS 把 `core` 不依赖 GUI 当成硬约束（CMake 层面可验证）；我们目前靠约定，没有机检（可加一条 import 方向检查）。

**值不值得抄**

- 值得抄「能力接口」这个概念，但不必抄 `QgisInterface` 的 200+ 个方法。我们只需要一个 10 个方法以内的 `PanelHost` 协议（取总线、取设置、发通知、注册命令、请求布局），让面板只依赖它。
- 不值得抄 `QgsApplication` 继承 `QApplication` 的写法。PySide6 侧用模块级单例 + 显式 `AppContext` 注入更可测；C++ 侧 `QgsApplication` 的做法可以借鉴「集中初始化顺序」，但不必让应用类继承 Qt 应用类。

## 3. 面板与停靠布局

**QGIS 的做法**

- `QgsDockWidget`（`src/gui/qgsdockwidget.h/.cpp`）在 `QDockWidget` 上加了三个概念：
  - `setUserVisible()/toggleUserVisible()/isUserVisible()`：**用户意图的可见性**，与 Qt 的 `isVisible()` 分开。程序性 `show()/hide()` 不会污染「用户上次是否收起」的判断。
  - `setToggleVisibilityAction(QAction*)`：把菜单项/快捷键与 dock 双向绑定，`visibilityChanged` 回写勾选状态。
  - `closed()/opened()` 信号：面板被用户关掉/打开时可做副作用（例如停掉定时器）。
- 布局持久化用 Qt 原生二进制：`QgisApp::saveWindowState()` 在 `QApplication::aboutToQuit` 时写 `QgsSettings` 的 `UI/state`（`saveState()`）与 `UI/geometry`（`saveGeometry()`），见 `src/app/qgisapp.cpp` 的 `saveWindowState/restoreWindowState`。`restoreState()` 的默认值是一段编译进二进制的 `defaultUIstate` 字节数组（`ui_defaults.h`）。
- 有一个真实的坑：由于 Qt 的 `QTBUG-89034`，`restoreState()` 被从构造函数移到 `showEvent`，否则 dock 几何恢复不正确（`qgisapp.cpp` 里保留的 `#if 0` 注释写明了原因）。
- 面板显隐的入口统一走 `QgsDockWidget::toggleUserVisible` 或 `setUserVisible`，快捷键（`showBookmarksDock` 等 `QShortcut`）与菜单勾选都接到这上面（`qgisapp.cpp` 中十余处 `connect(..., &QgsDockWidget::toggleUserVisible)`）。
- 面板本身由各功能模块创建，经 `QgisInterface::addDockWidget()` 挂到主窗口；主窗口不枚举面板清单。

**我们现在的做法**

- `desktop/panel_registry.py`：`PanelSpec`（`id/name/icon/area/collapsible/min_w/ratio_hint/closable/summary`）是**声明式面板清单**，`PanelRegistry` 单例只管元数据与 `attach_widget(id, widget)`，不造控件。新增面板改一处声明。
- `desktop/dock_layout_manager.py`：`DockLayoutManager` 按 id 建 dock，内置预设 `focus/analysis/grid`（`_preset_focus/_preset_analysis/_preset_grid`），支持 `capture_layout()/apply_layout_data()` 把**可读的 JSON 字典**（停靠区、tab 顺序、可见性、尺寸）存进 `desktop/layout_store.py`，而不是 Qt 二进制 blob；`build_collapse_strip()` 提供 36px 图标窄条折叠。
- `desktop/main_window.py` 在启动时恢复几何与布局，`layout_store` 对损坏配置做备份与 schema 校验。
- `cpp/` 侧对应的是 `cpp/src/ui/main_window.cpp` 与 `cpp/src/ui/layout_*`（C++ 移植版仍以 `saveState` 为主，见 `cpp/src/ui`）。

**差在哪**

| 维度 | QGIS | 我们 |
| --- | --- | --- |
| 清单 | 各模块自建 dock，接口挂载 | 集中 `PanelSpec` 声明 |
| 持久化 | `saveState()` 二进制 blob + 默认字节数组 | 结构化 JSON + schema + 损坏备份 |
| 用户意图 | `isUserVisible` 与 `isVisible` 分离 | 直接依赖 `QDockWidget.isVisible()` |
| 默认布局 | 编译期默认 blob | 三个显式预设 + 恢复失败回落 |
| 恢复时机 | 因 Qt bug 延后到 `showEvent` | 启动时恢复（未见同类延后） |

**代价与结论**

- QGIS 的二进制 blob 优点是「Qt 自己管，字段不用维护」，缺点是不可读、跨 Qt 版本脆弱、默认布局只能靠抓一份 blob、冲突时无法手工修。我们的 JSON 方案在这四点上更好，**不建议换成 blob**。
- 值得抄的只有一条：`QgsDockWidget` 的「用户意图可见性」。我们的折叠条/预设切换会程序性 `show()/hide()`，若与用户手动收起叠加，容易出现「切了预设后用户关掉的面板又弹回来」。加一个 `user_visible` 字段（我们已有 `_capture_tab_visible` 的可见性捕获，扩展到 dock 级）成本很小。
- 不建议抄 `defaultUIstate` 内嵌字节数组；我们已有预设函数，表达力更强。

## 4. 设置：单一真值源

**QGIS 的做法**

- 两层存储：`QgsSettings`（`src/core/settings/qgssettings.h/.cpp`）内部持有 `mUserSettings`（用户级 `QSettings`）与可选的 `mGlobalSettings`（管理员级 INI，`QSettings::IniFormat`）。`QgsSettings::init()` 读取 `setGlobalSettingsPath()` 设的路径；`allKeys()/childGroups()` 把两份合并，用户值优先。全局 INI 在 `src/app/main.cpp` 定位：先 `QStandardPaths::locateAll(... "qgis_global_settings.ini")`，再回落 `resources/qgis_global_settings.ini`。
- 每个设置项是一个**类型化对象**，不是裸字符串键：`QgsSettingsEntryBase`（`src/core/settings/qgssettingsentry.h`）构造参数 `(key, section, defaultValue, description, options)`，`mKey = section + "/" + key`；派生类在 `qgssettingsentryimpl.h`：`QgsSettingsEntryString/Bool/Integer/Integer64/Double/Color/StringList/EnumFlag/Variant`。
- 读写 API：`value(dynamicKeyPart)` / `setValue(v, dynamicKeyPart)` / `defaultValue()` / `exists()` / `remove()`；整数项在构造时带 `minValue/maxValue`，枚举项用 `QgsSettingsEntryEnumFlag<T>` 绑定 `QMetaEnum`，越界无法写入。
- 迁移支持：`Qgis::SettingsOption::SaveFormerValue` 让每次写入时保留旧值，配 `formerValue()` 读取（`qgis.h` 的 `SettingsOption` 枚举）；`SaveEnumFlagAsInt` 管枚举落盘格式。
- 发现与内省：`QgsSettingsTree::treeRoot()`（`src/core/settings/qgssettingstree.h`）建 `app/core/gui/...` 一级节点，设置项挂到 `QgsSettingsTreeNode`；`createPluginTreeNode(pluginName)` 给插件分配命名空间。旧机制 `QgsSettingsRegistryCore`（`src/core/settings/qgssettingsregistrycore.h`）以静态成员集中声明（如 `settingsDigitizingLineWidth`、`settingsDigitizingDefaultSnapMode`），现在被标记为待废弃，但仍用于枚举全部条目。
- 内省有实际消费者：`QgsAdvancedSettingsWidget`（`src/app/options/qgsadvancedoptions.cpp`）的 `createSettingsTreeWidget()` 直接遍历设置树生成「高级设置」页，不需要为每个键手写一行 UI。

**我们现在的做法**

- `desktop/config_schema.py` 是唯一声明处：`SCHEMA` 里每项含键名、类型、默认值、取值范围/枚举、分组、文案、`requires_restart`、存储后端、`source`（默认值出处）；`DEFAULTS` 从这里派生，`settings_panel.py` 只按 schema 渲染，不写第二份默认值。
- 校验有返回理由：`validate_value()` 返回 `(值, reason)`，越界夹取、未知枚举回默认，导入流程据 reason 汇报，不静默吞掉。
- 存储分三处，由 schema 的 `storage` 字段决定：`desktop_settings.json`（`DesktopSettings`，原子写 + 防抖 + 锁）、`~/.mbdsdr/gui_config.json`（观测站坐标）、`~/.mbdsdr/config.json`（AI 参数）。`DesktopSettings.load/get/set/reset/flush/add_change_listener` 是唯一读写口。
- 损坏处理：读失败时由 `settings.py:backup_corrupt_config()` 按时间戳把原文件改名为 `path.corrupt-YYYYmmdd-HHMMSS`（约 288 行），并用 `mbdsdr_ai.corrupt_evidence.write_reason()` 留下原因，而不是覆盖原文件。
- 默认值有出处且可机检：`tests/test_config_schema_source_symbols.py` 校验 `source` 引用的符号仍存在；它明确只能证明「符号还在」，不能证明「语义没变」。
- 环境覆盖：`MBDSDR_SETTINGS_DIR` 可整体改配置目录（`settings.py`）。

**差在哪**

| 维度 | QGIS | 我们 |
| --- | --- | --- |
| 存储 | 用户 `QSettings` + 管理员 INI 合并 | 三个 JSON 文件，按 schema 分后端 |
| 类型 | 编译期类型化对象（含 min/max、枚举绑定） | Python 侧 schema + 运行期校验 |
| 默认值 | `defaultValue` 在条目构造里 | schema 的 `default` + `source` 出处 |
| 内省 | 设置树可生成高级设置页 | schema 可遍历（设置页已由它生成） |
| 迁移 | `SaveFormerValue/formerValue` | 未见通用旧值保留；靠 schema 校验与备份 |
| 管理员覆盖 | 全局 INI，部署方改默认 | 只有目录级环境变量 |
| 校验反馈 | 类型/范围在写入时挡掉，少有人话理由 | 返回 reason，供导入流程汇报 |

**代价与结论**

- QGIS 的 `QgsSettingsEntry*` 本质是「把默认值、类型、范围、描述绑在一个对象上」，与我们的 schema 是同一思路；差别在前者用 C++ 类型系统、后者用数据描述。**我们不需要抄它的存储层**，但可以借两点：
  1. **`formerValue` 式的旧值保留**：我们已有损坏备份，却没有「合法但语义变化」的迁移记录（例如默认阈值从 -50 改到 -45，用户显式设过的值要保留、没设过的要跟随新默认）。在 schema 里加 `since`/`migrated_from` 比引入 QSettings 便宜。
  2. **管理员级默认覆盖**：现场部署常需要「这台机器默认静默阈值不同」。QGIS 用全局 INI 解决；我们可以加一个只读的 `defaults_override.json`（优先级低于用户值、高于代码默认），成本低于 QSettings。
- **不建议抄**把配置搬进注册表/INI。JSON + schema 的可读性、可 diff、可测试性都更好。
- 需要补的差异：我们缺「用户显式设置过」的标记（QGIS 用 `QgsSettings::value(key)` 是否 `contains` 区分）。没有它，改默认值时会误伤已设置用户，或让未设置用户永远停在旧默认。这是**真缺陷**，不是风格差异。

## 5. 长任务与进度

**QGIS 的做法**

- 任务抽象 `QgsTask`（`src/core/qgstaskmanager.h`）：
  - 子类只实现 `run()`（后台线程执行，返回 `bool` 表示成功/失败），主线程侧用信号收结果：`begun/progressChanged(0-100)/taskCompleted/taskTerminated/statusChanged`。
  - 状态机 `Queued/OnHold/Running/Complete/Terminated`；`cancel()` 只置 `mShouldTerminate` 标志，**协作式**，任务必须自己周期性检查 `isCanceled()` 并清理（头文件注释明确写了这一点）。`hold()/unhold()` 只对排队中的任务有效。
  - 展示策略是任务自带的 flag：`CanCancel`、`CancelWithoutPrompt`、`Hidden`（后台任务不进 GUI）、`Silent`（不发系统通知）。
  - 子任务：`addSubTask(task, deps, SubTaskDependency)`，`ParentDependsOnSubTask` 可表达「父任务必须等子任务完成」；子任务对用户不可见。
  - `setDependentLayers()`：图层被移除时任务自动取消——把「资源生命周期」接进了任务生命周期。
- 调度 `QgsTaskManager`：`addTask(task, priority)`、`addTaskWithDependencies`、`threadPool()`；内部用 `QThreadPool` + `QgsTaskRunnableWrapper` 跑 `QtConcurrentRun`（`src/core/qgstaskmanager.cpp` 的 `QgsTask::start()`、`mThreadPool->start(runnable, priority)`），不是每个任务一条裸 `QThread`。
- UI 侧有三层：`QgsTaskManagerWidget`（任务列表视图）、`QgsTaskManagerFloatingWidget`（浮动）、`QgsTaskManagerStatusBarWidget`（`QgsToolButton` + `QProgressBar`）。主窗口把状态栏控件作为永久控件挂上（`qgisapp.cpp`：`new QgsTaskManagerStatusBarWidget(...)`、`mStatusBar->addPermanentWidget(...)`），并把 `finalTaskProgressChanged/countActiveTasksChanged/statusChanged` 接到通知与提示。
- 退出语义：`QgsTask::CancelWithoutPrompt` 让关工程/关应用时不弹确认；`waitForFinished(timeout)` 提供有上限的同步等待。

**我们现在的做法**

- `desktop/receive_pipeline.py`：连续流用专用 `QThread` 子类（`IqReaderThread`、`FftWorker` 等）通过 `Signal/Slot` 把块送到 UI，`mbdsdr_ai/dsp_stream.py:PingPongStream` 做零拷贝交接（`receive_pipeline` 只 import 使用）；这是**流式**模型，不是「一个有开始和结束的任务」。
- 短任务用 `QRunnable` + `QThreadPool.globalInstance()`（`desktop/device_panel.py` 的 `_DeviceEnumTask`），不阻塞事件循环；`desktop/location_panel.py` 的城市搜索用 `_SearchWorker(QThread)`；`desktop/ai_panel.py` 用 `QThread` 跑模型调用。
- 进度呈现分散在各面板：瓦片下载（`desktop/osm_map.py` 的 `RegionDownloader`）、AI 请求、频谱扫描各自画进度或忙碌态；没有全局「正在运行什么」的单一入口，也没有统一取消语义。
- 取消多为「停止线程/丢弃结果」，没有 `isCanceled` 式的协作检查点；长循环（FFT、批量解码）中途不可中断。

**差在哪**

1. QGIS 把「任务」提升为一等对象，调度、进度、取消、通知、退出语义都在一处；我们的后台工作按用途分散，用户无法在一个地方看到「还有 3 个任务在跑」。
2. QGIS 的协作式取消要求任务自己配合；我们的 `QThread.terminate()` 式思路要么不用（多数是设 flag），要么直接丢结果，缺少统一契约。
3. QGIS 有依赖图与资源依赖（图层移除→任务取消）；我们的场景里对应的是「设备断开→所有采集/解码任务应终止」，目前靠各模块自己监听设备状态，容易漏。
4. 线程模型不同：QGIS 统一 `QThreadPool`；我们混用 `QThread` 与 `QThreadPool`。混合本身不是问题（流式用专用线程是对的），但**任务可见性**因此更难统一。

**值不值得抄**

- **不抄 `QgsTask/QgsTaskManager` 整体**：600+ 行调度器 + 3 个控件 + 模型/视图，换来的主要是「任务列表 UI」；我们的面板数远少于 QGIS，成本不划算。
- 值得抄三个小概念，成本各在几十行以内：
  1. **`Job` 协议**：`description/progress/cancel()/is_canceled`，短任务（设备枚举、瓦片下载、AI 请求、批量解码）实现它，注册到一个小 `JobRegistry`，状态栏放一个「N 个任务」按钮，点开是列表。
  2. **协作取消契约**：长循环里加 `if job.is_canceled: break`，而不是 `terminate()`；这与我们已有的 `QThread` 结构兼容。
  3. **`Hidden/Silent` 两个布尔**：后台任务默认不进列表、不弹通知；否则「万物皆任务」会变成噪音。
- 不抄子任务/依赖图：我们的流水线是持续流，不是 DAG；硬套会把 `receive_pipeline` 的实时性搞坏。
- 一个可以直接落地的缺口：**设备断开时统一取消**。QGIS 用 `setDependentLayers` 做「资源没了就取消任务」；我们可在设备状态变化处广播一次 `device_lost`，由 `JobRegistry` 统一取消所有依赖该设备的 job，避免各面板各写一遍。

## 6. 错误、告警与降级

**QGIS 的做法**

- 日志与提示分离：`QgsMessageLog::logMessage(message, tag, level, notifyUser, file, function, line)`（`src/core/qgsmessagelog.h`）只有一个入口，但 `notifyUser` 决定「这条要不要打扰用户」；级别是 `Qgis::MessageLevel` 的 `Info/Warning/Critical/Success/NoLevel`（`src/core/qgis.h`）。源码位置用 `__builtin_FILE/FUNCTION/LINE` 自动带上，调用方不用手写。
- 日志的消费端是 GUI 的 **Log Messages 面板**（`src/gui/qgsmessagelogviewer.*`）与无界面时的 stderr 实现；源码树里没有内建的轮转日志文件，落盘由发行方/插件自己接。`QgsMessageLogNotifyBlocker` 可以在批量操作期间临时压制「有新错误」的提示，避免一次导入弹几百条。
- 用户可见的即时反馈是 `QgsMessageBar`（`src/gui/qgsmessagebar.h`）：**非模态**、按级别着色、自动堆叠（只显示最新一条，逐条关闭后显示下一条，空了自动隐藏）；`pushMessage(text, level, duration)` 的 `duration=0` 表示必须手动关，`-1` 表示用该级别的默认超时；`pushWidget()` 可塞入带按钮的自定义控件（例如「重试」「打开设置」）。
- 加载失败有专门的恢复路径：`QgsProjectBadLayerHandler` 子类 `QgsHandleBadLayersHandler` + 对话框 `QgsHandleBadLayers`（`src/app/qgshandlebadlayers.h/.cpp`）。它列出坏图层的数据源、允许逐个浏览替换、`autoFind()` 在候选基路径里自动找同名文件、`apply()` 批量写回；找不到时用户可以选择忽略而不是整个工程打不开。
- 长输出（例如 SQL/驱动报错）走 `QgsMessageOutput`/`QgsMessageViewer`，与短消息的 message bar 分开，避免把一大段堆栈塞进状态栏。

**我们现在的做法**

- 错误有**编码与处置库**：`mbdsdr_ai/error_catalog.py` 是错误码 → 用户文案/下一步动作的目录；`desktop/error_remedy.py` 提供 `remedy_for_code()`、`no_entry_reason()`、`mapping_gaps()/mapping_overlaps()`（机检目录与代码的覆盖关系）、`classify_connect_error()/humanize_connect_error()`、`build_link_label()/build_diagnostics_link()/open_remedy()`。
- 呈现以**模态对话框**为主：各面板大量 `QMessageBox.warning/information`（书签、AI、设备等），错误弹窗通过 `build_link_label()`/`open_remedy()` 挂「查看处置」链接。
- 诊断有专门面板：`desktop/diagnostics_panel.py` + `diagnostics_data.py`，另有 `desktop/troubleshooting.py` 提供静态排查指引。
- 日志：`desktop/logging_setup.py` 的 `configure_logging()/configure_from_settings()` 只写 stderr；打包版由 `main.py:_ensure_stdio_for_pythonw()` 把 stderr 接到启动日志文件，函数本身不建文件、不做轮转。

**差在哪**

| 维度 | QGIS | 我们 |
| --- | --- | --- |
| 错误目录 | 无集中目录，靠文案 | `error_catalog` + 覆盖机检 |
| 即时反馈 | 非模态 message bar，可堆叠、可带按钮、可超时 | 模态 `QMessageBox`，一次一条 |
| 静默/打扰 | `notifyUser` 显式区分 | 有日志级别，但「是否弹窗」由各调用点自行决定 |
| 批量抑制 | `QgsMessageLogNotifyBlocker` | 无 |
| 坏数据修复 | 坏图层对话框：自动找文件、批量应用、可忽略 | 未见等价的交互式修复；诊断面板是只读信息 |
| 长输出 | `QgsMessageOutput` 独立查看器 | 混在对话框/日志里 |

**值不值得抄**

- **值得抄：非模态消息条**。SDR 应用在采集/解码时弹模态框会打断操作，且多个错误会叠成「弹窗地狱」。做一个 `NotifyBar`（级别、超时、堆叠、可选动作按钮）成本低，且与现有 `error_catalog` 天然衔接：有 remedy 的条目给按钮，没有的只记录。
- **值得抄：`notifyUser` 与本项目 error_catalog 的结合**。可以定规则——目录里能给出「用户可执行动作」的错误才弹条/弹窗，纯内部异常只进日志。这比按日志级别判断更准，也能减少「未知错误」式打扰。
- **值得抄：批量抑制**。导入书签/批量解码时用一个上下文管理器压制通知，结束后汇总「N 条失败，查看详情」。这是 QGIS `QgsMessageLogNotifyBlocker` 的直接移植。
- **值得抄一半：坏数据自动找文件**。我们的场景对应「录音目录被移动」「TLE 文件缺失」「部署路径变化」。QGIS 的 `autoFind()` 思路（在若干候选根目录下按文件名找、找到后批量替换）可以直接用；但不需要它的 XML 数据源模型。
- **不建议抄** `QgsMessageLog` 的全局单例与 `QgsMessageOutput` 体系。我们已经用 Python `logging` + `error_catalog` 解决了同样问题，且错误码比 tag 更有用。

## 7. 插件式注册表

**QGIS 的做法**

- C++ 插件契约极薄：`QgisPlugin`（`src/plugins/qgisplugin.h`）只带 `name/description/category/version/PluginType`，加两个必须 `extern "C"` 的符号 `classFactory(QgisInterface*)` 与 `unload()`；插件真正的入口是 `initGui()`。
- 生命周期集中在 `QgsPluginRegistry`（`src/app/qgspluginregistry.h/.cpp`）：`instance()` 单例、`loadCppPlugin(fullPath)`、`loadPythonPlugin(packageName)`、`unloadCppPlugin/unloadPythonPlugin`、`unloadAll()`、`restoreSessionPlugins(pluginDirList)`、`isLoaded(key)`。加载失败走 `QgsMessageLog` + message bar，不让主程序崩。
- Python 侧是另一套但同构：`python/utils.py` 的 `findPlugins(path)` 扫目录（要求 `__init__.py` + `metadata.txt`）、`updateAvailablePlugins(sort_by_dependencies)` 建可用清单并按 `plugin_dependencies` 拓扑排序（`_sortAvailablePlugins/_move_plugin/get_plugin_deps`）、`loadPlugin()` → `import`、`_startPlugin()` → `classFactory(iface)`、`startPlugin()` → `initGui()`、`unloadPlugin()`；`pluginMetadata()` 读 `metadata.txt` 的 `[general]`。
- 版本兼容与依赖：`metadata.txt` 里声明 `qgisMinimumVersion/qgisMaximumVersion/plugin_dependencies`；加载前检查，失败给出「哪个插件、缺什么」而不是静默跳过。
- 内部注册表是第三种，也是用得最多的一种：数据提供者 `QgsProviderRegistry`（`src/core/providers/qgsproviderregistry.h`）、符号层 `QgsSymbolLayerRegistry`（`src/core/symbology/qgssymbollayerregistry.h`）、渲染器、Processing 算法、定位器过滤器等。统一形态是「元数据对象 + 工厂函数」：`QgsSymbolLayerAbstractMetadata::createSymbolLayer(map)`，`QgsSymbolLayerMetadata` 持 `mCreateFunc`；注册表按字符串类型键查表创建，核心代码不写 `switch(type)`。

**我们现在的做法**

- 面板：`desktop/panel_registry.py` 的 `PanelRegistry`（`PanelSpec` 静态声明 + `attach_widget`），是**编译期清单**，不支持第三方目录发现。
- 解调模式：`desktop/mode_registry.py` 提供 `register(mode)/unregister(name)/get(name)/list_modes(category)/mode_names()` 与 `DemodMode` 描述对象；`config_schema` 的合法模式集合直接取自这里，避免第二份清单。
- AI 工具：`mbdsdr_ai/tool_registry.py` 的 `ToolRegistry` 是**带策略的注册表**：`register(name, definition, handler, available, category, parallel_safe, description_i18n)`、`unregister()`、`set_available()`、`list_tools(include_unavailable)`、`get_tool_definitions()`、`register_mcp_tools()`；另有参数校验 `validate_arguments()`、写工具判定 `is_write_tool()`、并发白名单 `is_parallel_safe()`、每工具超时 `_run_handler_with_timeout()`、调用日志 `ToolCallLog`。
- `mbdsdr_ai/plugins/` 目录目前为空；没有从文件系统加载第三方插件的机制，也没有 `metadata.txt` 式的版本/依赖声明。

**差在哪**

| 维度 | QGIS | 我们 |
| --- | --- | --- |
| 发现 | 扫目录 + `metadata.txt` + `plugin_dependencies` 拓扑排序 | 全部静态 import/声明 |
| 生命周期 | load → classFactory → initGui → unload，可运行期启停 | 进程内注册，无卸载/热插拔 |
| 隔离 | C++ 动态库 + Python 包，失败只影响单个插件 | 同进程 Python，失败即全局异常 |
| 能力策略 | 基本没有（插件想干什么都行） | ToolRegistry 有写/并发/超时/可用性策略 |
| 类型扩展 | 注册表 + 工厂（符号层、提供者、算法） | 模式注册表 + 工具注册表，面板不可扩展 |
| 版本兼容 | 显式 min/max + 依赖检查 | 无（单体应用，不需要） |

**值不值得抄**

- **不建议抄插件发现/加载**。我们没有第三方生态，也没有「用户自己写插件」的需求；引入目录扫描 + 动态 import 会立刻带来安全、版本、崩溃隔离三类成本，收益接近零。`mbdsdr_ai/plugins/` 空目录反而说明这条线没需求。
- **值得抄的是「元数据 + 工厂」的注册表形态**，用在两处具体地方：
  1. **解码器/协议**：现在 `mode_registry` 只有参数（带宽、音频截止），解码实现仍分散。若要做「新增一个协议只改一处」，应把 `DemodMode` 扩展为 `create_decoder()` 工厂，与 QGIS `QgsSymbolLayerMetadata::createSymbolLayer` 同构；收益是测试可注入假解码器，也便于按能力（是否支持 IQ 录制、是否支持软判决）查询。
  2. **面板/视图**：`PanelSpec` 已有元数据，但没有工厂；面板仍由 `MainWindow` 硬编码构造。加一个 `factory: Callable[[PanelHost], QWidget]` 字段，才能让「注册即出现」，否则注册表只解决了一半问题。
- **值得抄「失败隔离 + 明确报错」**：QGIS 加载插件失败只影响该插件，并在 message bar 说清「哪个插件、哪个阶段（classFactory/initGui）失败」。我们的 `mode_registry.register` 目前是进程内直接调用，若某个模式初始化抛异常会打断整条注册链；加 try/except + 记录来源是低成本改进。
- **不建议抄** QGIS 的 `PluginType` 枚举与 C++ `extern "C"` 约定；Python 侧用协议/ABC 更自然。

## 8. 翻译、主题与资源分发

### 8.1 翻译

**QGIS 的做法**

- `QgsApplication::setTranslation(locale)/translation()`（`src/core/qgsapplication.cpp`）在 `init()` 里安装翻译器，按顺序加载三类 `.qm`：`qgis_<locale>`、`qt_<locale>`、`qtbase_<locale>`（Qt 自带控件文案），路径来自 `QgsApplication::translationPath()`。`QgsApplication::locale()` 是全局语言入口。
- 没有运行期语言切换：改语言要重启（`qgsoptions.cpp` 里改完提示重启）。
- Python 插件**没有**统一翻译管线：`python/utils.py` 里没有 `QTranslator`/`.qm` 相关代码，插件要么自带翻译，要么只用英文/中文源文。
- `.ts` 由 Transifex 同步（`.tx/config`），构建期 `lrelease` 生成 `.qm`，安装到 `share/qgis/i18n`。

**我们现在的做法**

- `desktop/l10n.py`：`SUPPORTED_UI_LANGUAGES`、`LANGUAGE_SELF_NAMES`、`normalize_ui_language()`、`qm_search_dirs()`、`install_translator(app, tag)`。源语言是 `zh`（不装翻译器，`tr()` 直接回源文）；`en/ja` 加载 `desktop_<tag>.qm`。找不到 `.qm` 时**只警告一次并保持源语言**，不装半坏翻译。
- `.qm` 在构建期由 `desktop/i18n/build_qm.py` 生成；当前仓库里只有 `desktop_en.qm/.ts`、`desktop_ja.qm/.ts`。
- `cpp/CMakeLists.txt` 用 `find_package(Qt6 COMPONENTS LinguistTools)` + `mbdsdr_en.ts/mbdsdr_ja.ts`，`lrelease` 产物拷到可执行文件旁 `i18n/`；`cpp/src/core/l10n.cpp` 按同一口径搜索；没有 LinguistTools 的机器跳过管线并回退源语言。

**差在哪**

| 维度 | QGIS | 我们 |
| --- | --- | --- |
| Qt 自身文案 | 加载 `qt_*.qm`、`qtbase_*.qm` | 未加载；Qt 内置按钮（如 `QMessageBox` 的 OK/Cancel）随系统语言 |
| 语言切换 | 重启生效 | 同样重启生效（设置页提示） |
| 缺失回退 | 静默回退英文 | 一次性 `qWarning` + 源语言 |
| 插件翻译 | 无统一机制 | 无插件机制，问题不存在 |
| 构建 | lrelease + Transifex | lrelease + `build_qm.py`（Python）/ `LinguistTools`（C++） |

**值不值得抄**

- 值得抄一条：**加载 `qtbase_<locale>.qm`**。我们只翻了应用文案，Qt 自带的「OK/Cancel/Apply」「Print」「Save」等仍是英文（或系统语言），中日文界面会中英混排。Qt 安装目录下自带 `translations/qtbase_zh_CN.qm`，用 `QLibraryInfo.path(QLibraryInfo.TranslationsPath)` 找，几行代码。
- 不建议抄 Transifex/`.tx` 流程，我们的 `build_qm.py` 足够。
- 不建议做运行期热切换：QGIS 都选择重启，说明成本高于收益。

### 8.2 主题与样式

**QGIS 的做法**

- 主题有两种含义：`QgsApplication::themeName()`（图标主题，决定 `getThemeIcon()` 去哪找 SVG）与 `setUITheme()`（QSS 主题）。`uiThemes()` 枚举有效主题目录，**目录必须含 `style.qss`** 才算有效。
- `QgsApplication::setUITheme()`（`src/core/qgsapplication.cpp` 约 1071 行）：读 `style.qss`，把 `@theme_path` 替换成主题绝对路径；若同目录有 `variables.qss`，逐行把 `@变量名` 替换为值；然后 `qApp->setStyleSheet(...)`。主题选 `default` 或不存在时清空样式表。
- 动态部分由 `QgisAppStyleSheet`（`src/app/qgisappstylesheet.h`）负责：`defaultOptions()` 收集平台/字体/控件尺寸等可调项，`applyStyleSheet(opts)` 生成 QSS 并发 `appStyleSheetChanged`，`QgisApp::setAppStyleSheet()` 再级联给独立的布局设计器窗口（`qgisapp.cpp:3361`）。用户字体大小/族也在这里（`userFontSize()/userFontFamily()`）。
- 图标：`QgsApplication::getThemeIcon(name, fillColor, strokeColor)` 按 `themeName()/icons/` → 默认主题 → `images/` 的顺序找，支持用指定颜色重绘 SVG。
- 资源落盘：`cmake/CopyResources.cmake` 在构建/安装时把 `resources/data`、`resources/themes`、`cpt-city`、`symbols` 拷过去；只有 3D 纹理、OAuth2、插件图标等少量资源用 `.qrc` 编进二进制（`images/images.qrc`、`resources/3d/textures/textures.qrc` 等）。

**我们现在的做法**

- `desktop/themes.py`：**令牌 → QSS 生成**，而不是静态 `.qss` + 变量替换。`get_app_font()`、`fit_scale_to_screen()`、`qss_font_size()`、`requested_font_scale()/set_font_scale_override()`、`_control_coverage_qss()`（逐控件覆盖，防遗漏）、`_asset_dir()/_spin_arrow_url()/_check_mark_url()`（运行期生成 SVG 资源）。
- `desktop/tokens.py` 提供颜色/间距令牌；深浅色不是两套目录，而是同一套令牌的取值切换。
- `cpp/` 侧同一思路：`cpp/src/core/tokens.h` 的 `tokens::buildDarkQss()` 生成整份 QSS，`cpp/src/main.cpp` 在 `QApplication` 上设一次，`cpp/src/ui/main_window.cpp` 与 `calibration_dialog.cpp` 再对少数控件单独覆盖；`cpp/res/` 只放色图 JSON（`colormaps/*.json`），不放样式文件。

**差在哪**

| 维度 | QGIS | 我们 |
| --- | --- | --- |
| 样式来源 | 主题目录 `style.qss` + `variables.qss` 文本替换 | Python 里用令牌拼 QSS |
| 主题枚举 | `uiThemes()` 扫目录，要求 `style.qss` | 固定几套令牌，无目录发现 |
| 用户可调 | 字体大小/族、控件尺寸等一批选项 | 字体缩放（1.0/1.25/1.5）+ 屏幕适配 |
| 图标着色 | `getThemeIcon(name, fill, stroke)` 运行期重绘 | `themes.py` 运行期生成 SVG（`_spin_arrow_url` 等） |
| 独立窗口级联 | 显式给布局设计器设同一 QSS | 单主窗口，无此问题 |
| 资源 | 目录拷贝 + 少量 qrc | PyInstaller `datas` + 运行期生成 |

**值不值得抄**

- **不建议抄主题目录 + `style.qss` 文本替换**。我们的令牌方案类型更安全（令牌名拼错在 Python 里能测出来，QSS 里的 `@变量` 拼错只会静默留空），且不用维护两套主题文件。
- **值得抄「控件覆盖清单」的思路，但我们已经有了**：`_control_coverage_qss()` 逐控件写规则，正是为了避免 QSS 继承漏项。QGIS 的做法是靠 `style.qss` 里大而全的规则；我们更可控。
- **值得抄一半：`getThemeIcon` 的参数化着色**。它把「同一图标的常态/禁用/高亮」用 fill/stroke 两个参数解决，不用为每个状态准备三份资源。我们已经用运行期生成 SVG 达到类似效果，**差别是我们只对少数图标这么做**；若以后图标状态变多，按这个模式扩展即可，不必换主题体系。
- 不建议抄 `uiThemes()` 的目录发现：没有第三方主题需求。

### 8.3 资源随包分发

- QGIS：`CopyResources.cmake` 把资源目录整体拷到构建树/安装树，运行期按 `pkgDataPath()` 相对定位；`.qrc` 只用于必须内嵌的少量资源。好处是资源可被用户/打包方替换，坏处是「安装目录必须完整」，丢一个目录就缺图标。
- 我们：`desktop/MBDSDR.spec` 用 PyInstaller 的 `datas` 显式列目录，`cpp` 用 CMake install/`qt_add_resources`；资源缺失在打包时就暴露，而不是运行期。
- 结论：**不建议改成 QGIS 的「散目录 + 运行期相对定位」**。我们的打包形态（单目录分发、无系统级安装）更适合显式清单；但可以借它一条：资源路径统一入口（QGIS 用 `pkgDataPath()`，我们目前散落在 `themes._asset_dir()`、`l10n.qm_search_dirs()`、`osm_map` 的缓存目录等处）。统一成一个 `resource_path(kind)` 能减少打包漏项。

## 9. 发布打包

**QGIS 的做法**

- 版本号集中在顶层 `CMakeLists.txt`：`CPACK_PACKAGE_VERSION_MAJOR/MINOR/PATCH`（3/44/15），派生出 `COMPLETE_VERSION` 与整数版 `QGIS_VERSION_INT = major*10000 + minor*100 + patch`；`cmake_templates/qgsconfig.h.in` 注入头文件，运行期 `QgsApplication::version()`/`QGIS_VERSION` 使用。
- 安装规则分散在各子目录：`src/app/CMakeLists.txt` 的 `install(TARGETS qgis_app RUNTIME DESTINATION ${QGIS_BIN_DIR})`、`install(FILES qgis.ico ... DESTINATION icons)`；macOS 用 `CREATE_MACOSX_BUNDLE` + `mac/app.info.plist.in` 生成 `.app`。
- **本树没有 `windeployqt`/`macdeployqt` 调用**。Windows 的完整安装包由 OSGeo4W / QGIS Standalone 等外部打包仓负责；`ms-windows/` 只有 `cygwin/package.sh`、`mingw/build.sh`、`dev/qgis.env.in` 这类开发辅助。也就是说，QGIS 不是一个「照着就能打出安装包」的样板。
- 运行期定位靠前缀路径：`QGIS_PREFIX_PATH` 环境变量（`qgsapplication.cpp` 多处读取）或可执行文件相对位置推导 `prefixPath/pkgDataPath/pluginPath`；用户配置目录由 `QGIS_CUSTOM_CONFIG_PATH` 覆盖，命令行 `-S/--profiles-path` 指定 profile 根。
- 部署侧还有一个值得注意的开关：`-C/--nocustomization` 与 `-z/--customizationfile path`（`src/app/main.cpp`），配合 `QgsCustomization` 用 INI 隐藏/禁用菜单项和面板，给「只允许用部分功能」的现场部署用。

**我们现在的做法**

- `desktop/MBDSDR.spec`：PyInstaller **onedir**（`console=False`），`datas` 显式列 `assets/` 与 `mbdsdr_ai` 数据文件，`hiddenimports` 用 `collect_submodules('PySide6')`、`collect_submodules('mbdsdr_ai', filter=...)`（排除 `mbdsdr_ai.tests`），另有 `_collect_namespace_submodules('scipy', '_external')` 按目录扫 PEP 420 命名空间包（`collect_submodules` 枚举不到，冻结版启动即 `No module named 'scipy._external.array_api_compat.numpy.fft'`）；`astronomy.py` 等动态导入单独补进 `datas`。
- `cpp/CMakeLists.txt`：`cmake/deploy_runtime.cmake` + `add_custom_target(deploy_win_runtime)`，并在构建后自动部署（把 `librtlsdr` 等 DLL 拷到 exe 旁）；末尾有 `install()`/CPack 段（注释标明是「零安装/打包」的 P0 缺口）。
- 配置目录：`MBDSDR_SETTINGS_DIR` 可覆盖（`settings.py`），作用与 QGIS 的 `QGIS_CUSTOM_CONFIG_PATH` 相同。

**差在哪**

| 维度 | QGIS | 我们 |
| --- | --- | --- |
| 打包工具 | CPack + 外部 OSGeo4W/Standalone | PyInstaller（Python）/ CMake install+CPack（C++） |
| 依赖部署 | 前缀目录布局，系统级依赖 | 显式拷贝 DLL（`deploy_runtime.cmake`） |
| 数据文件 | 资源目录整体拷 | `datas` 显式清单 + 动态导入补丁 |
| 配置目录覆盖 | 环境变量 + 命令行 `--profiles-path` | 环境变量 `MBDSDR_SETTINGS_DIR` |
| 部署裁剪 | `QgsCustomization` INI 隐藏功能 | 布局预设 + 面板 `closable`，无「锁定功能」机制 |
| 版本注入 | 单一 CMake 源 → `qgsconfig.h.in` | 单一文件 `mbdsdr_ai/VERSION` → pyproject `dynamic`、CMake `configure_file`、spec 的 EXE 版本资源 |

**值不值得抄**

- **不建议把 QGIS 的打包方式当模板**：它自己都把 Windows 安装包交给外部仓库，本树只有零散脚本。我们的 PyInstaller + `deploy_runtime.cmake` 更贴近实际交付形态。
- **单一版本号源：我们已经做到了，不必抄**。QGIS 用 `CPACK_PACKAGE_VERSION_*` 一处生成 `QGS_VERSION`/`QGIS_VERSION_INT`；我们是 `mbdsdr_ai/VERSION` 一个文件，被 `pyproject.toml`（`version = {file = ...}`）、`cpp/CMakeLists.txt`（`file(READ)` → `configure_file` 生成 `mbdsdr_version.h`）、`desktop/MBDSDR.spec`（EXE 版本资源）三处读取。差别只在 QGIS 还派生了一个整数版 `QGIS_VERSION_INT` 供比较大小；我们若要「按版本号做兼容判断」，可以照抄这个 `major*10000+minor*100+patch` 的整形，成本几行。
- **值得抄（条件性）：部署裁剪配置**。如果存在「客户现场只开放接收+录制，不给发射/实验功能」的需求，QGIS 的 customization INI 思路（按对象名隐藏菜单/面板/工具栏）比编译期宏灵活。我们没有这种需求证据，先记为「待确认」，不直接实现。
- **值得抄：`--profiles-path` 式的显式 profile 根**。我们有环境变量，但没有命令行参数；现场支持时让用户能临时用另一套配置启动（不动默认目录）很有用，成本一个 argparse 项。

## 10. GIS 能力清单：我们能加什么

判断标准只有一条：**加上去，用户能多做成一件他今天做不成的事吗**。下面每项都先写「我们现在有什么」，再写 QGIS 怎么做，再算代价，最后回答「不加会怎样」。

### 10.1 坐标参考系与投影变换

**我们现在**：只有 WGS84 / WGS-72 两个固定的椭球族，没有可切换的 CRS 体系。
- `mbdsdr_ai/geodesy.py:CoordinateConverter`：`ecef_to_llh/llh_to_ecef/ecef_to_enu/enu_to_ecef/geodist/satazel`，WGS84 椭球，来自 RTKLIB 的 `ecef2pos/pos2ecef`。
- `mbdsdr_ai/orbit.py:geodetic_to_ecef` 另有一份**WGS-72** 经纬高→ECEF（公里，与 SGP4 内核同族）；`compute_satellite_state` 走 TEME→ECEF（GMST 旋转）→ENU。
- `desktop/osm_map.py:lonlat_to_world/world_to_lonlat` 是 Web Mercator；`desktop/rf_sky_view.py` 的天球投影在 `mbdsdr_ai/celestial_geometry.py`：`StereographicProjection/OrthographicProjection/AzimuthalEquidistantProjection/PerspectiveProjection`，是**天球**投影，不是地面地图投影。
- 没有 EPSG 注册表、没有基准转换、没有高斯-克吕格/UTM，也没有 GCJ-02/BD-09 偏移处理。

**QGIS 怎么做**：`QgsCoordinateReferenceSystem`（`src/core/proj/qgscoordinatereferencesystem.h`）支持 EPSG/WKT/PROJ 字符串，入口是 `createFromOgcWmsCrs("EPSG:4326")`、`createFromSrsId()`、`createFromId()`（已标废弃），另有 `authid()/toWkt()/mapUnits()/ellipsoid()`；`QgsCoordinateTransform`（`qgscoordinatetransform.h`）的 `setSourceCrs()/setDestinationCrs()/transform(QgsPointXY)` 由 PROJ 执行；CRS 元数据来自 `resources/srs6.db`，基准网格来自 PROJ 数据目录。地图渲染时每个图层按「图层 CRS → 画布 CRS」变换（`QgsMapLayer::crs()` + `QgsMapCanvas::mapSettings()`）。

**代价**：PROJ 本体 + `proj.db`（约 10 MB 级）+ 可选网格文件；Python 侧 `pyproj` wheel 约 5–10 MB。API 面不小（CRS 解析、轴序、变换上下文、坐标轴方向），还要处理「投影坐标单位是米、地理坐标是度」的两套语义。

**不加会怎样**：今天的所有输入都是 WGS84（卫星、ADS-B、OSM），**不受影响**。真正会卡住的只有两种场景：导入别人给的 CGCS2000 高斯平面坐标/地方坐标，或在中国境内把 WGS84 点叠到偏移过的国内底图上。后者 PROJ 也解决不了（GCJ-02 不是标准 CRS，QGIS 同样没有内置）。

**结论**：**不引入 PROJ**。如果将来有「导入地方坐标」的需求，先做一个小模块（UTM/高斯正反算 + 七参数），按需加载；GCJ-02/BD-09 是独立的小偏移公式，与 GIS 栈无关。**这项抄 QGIS 的代价远大于收益。**

### 10.2 椭球面距离、方位与面积

**我们现在**：`mbdsdr_ai/adsb_map.py:haversine_km` 是**球面**大圆距离（`desktop/adsb_map_panel.py` 的距离列用它）；`geodesy.CoordinateConverter.geodist()` 是三维几何距离 + Sagnac 改正（GNSS 用），不是椭球面距离；`satazel()` 给方位/仰角。没有椭球面面积、没有「给定起点+方位+距离求终点」。

**QGIS 怎么做**：`QgsDistanceArea`（`src/core/qgsdistancearea.h`）的 `setEllipsoid()/setSourceCrs()/measureLine(p1,p2)/measureLine(points)/bearing(p1,p2)/measurePolygon()/measureLineProjected()`；底层直接 include PROJ 的 `struct geod_geodesic`（Karney 测地线，`qgsdistancearea.h:29`），所以是椭球面精确解，不是 haversine。

**代价**：不引 PROJ 的话，用 `geographiclib`（纯 Python，约百 KB）或自己写 Vincenty（约 60 行，极点附近需退化处理）。测试要覆盖赤道、极区、跨 180° 经线、零长度。

**不加会怎样**：球面 vs 椭球在 1000 km 量级差约 0.3%（约 3 km）；对「飞机距离本站多远」「两个地面站相距多远」这类展示，用户看到的是错几公里的数。对卫星仰角/过境预测没有影响（那条链用三维几何，是对的）。

**结论**：**值得换，但不值得为此引入 GIS 栈**。把 `haversine_km` 升级为 `geodesic_km`（`geographiclib.geodesic.Geodesic.WGS84.Inverse`），并在 `CoordinateConverter` 旁加 `direct()`（起点+方位+距离→终点，用于画覆盖圈）。优先级中低，只改用户可见的距离/方位展示。

### 10.3 地图画布与图层栈

**我们现在**：`desktop/osm_map.py:OsmMapView` 是自绘瓦片地图：`lonlat_to_world/world_to_lonlat`、`TileCache/TileLoader`、`RegionDownloader`（离线区域下载）、`add_layer(name, painter_cb)/set_overlay` 式叠加层、`set_style()` 三种底图、`_PinchMixin` 触屏缩放。使用方是 `location_panel.py`（位置/地图提示）与 `adsb_map_panel.py`（ADS-B 图层）。叠加内容是「点/折线/文字」，由回调直接 `QPainter` 画。
没有图层树、没有任意 CRS 图层、没有矢量/栅格数据导入、没有图层透明度/顺序 UI、没有打印排版。

**QGIS 怎么做**：`QgsMapCanvas`（`src/gui/qgsmapcanvas.h`）管 `setLayers()/setDestinationCrs()/setExtent()/refresh()`，图层是 `QgsMapLayer` 子类（`QgsRasterLayer/QgsVectorLayer`），CRS 变换在渲染任务里做；`QgsMapCanvasItem`（`qgsmapcanvasitem.h`）提供 `paint()/boundingRect()/toCanvasCoordinates()` 的自定义叠加物；工程由 `QgsProject` 持有图层树。渲染是独立的 `QgsMapRendererJob`，支持多线程瓦片/要素绘制。

**代价**：这不是「加一个类」，是把 GDAL/OGR/GEOS + 渲染管线 + 图层模型 + 工程模型整套搬进来；仅 `src/core/raster`、`src/core/vector`、`src/core/layertree`、`src/gui` 的相关部分就是数十万行。Python 侧没有「半个 QgsMapCanvas」可用。

**不加会怎样**：用户不能把自带的 GeoTIFF/Shapefile/GPX 当图层打开，不能调图层顺序/透明度，不能打印地图。**这些都不是 SDR 接收应用的核心任务**；我们需要的叠加物（卫星点、航迹、覆盖圈、站点）已经能用回调画。

**结论**：**不抄**。`OsmMapView` 的抽象层级是对的；要扩展就扩展它的叠加层 API（例如传 `QPainterPath`/经纬度折线），不要换成 `QgsMapCanvas`。若哪天真要显示用户栅格，离线切片后当瓦片源，比嵌入 GDAL 便宜得多。

### 10.4 瓦片底图与缓存

**我们现在**：`osm_map.py` 已有 `TileCache`（磁盘+内存）、`TileLoader`（`QNetworkAccessManager` + 线程池解码）、`STYLES`（OSM/CARTO 明暗）、`style_for_dark()`、`RegionDownloader` 离线预取、`OsmMapView` 的缩放/平移/捏合。也就是说这项**已经做完了**。

**QGIS 怎么做**：XYZ 瓦片不是独立 provider，而是 `src/providers/wms/qgsxyzconnection.*` + `QgsRasterLayer` 的 `type=xyz` URI；瓦片缓存走 `QgsNetworkAccessManager` 的 `QNetworkDiskCache`；图层树里表现为普通栅格图层，可调透明度/重采样。

**差在哪**：QGIS 支持任意 URL 模板、认证、瓦片矩阵集（非 Web Mercator）、多图层叠加；我们固定三种样式、只支持 Web Mercator（对 2D 地图够用）、缓存策略自管。

**结论**：**不抄**。我们的实现与需求匹配；唯一可借的是 QGIS 的「缓存大小上限 + 淘汰」显式配置（我们若已有容量上限可忽略）。这项在对照表里应记为「已用另一种方式解决」。

### 10.5 星下点、地面轨迹与覆盖圈

**我们现在**：**没有**。`mbdsdr_ai/orbit.py` 能算 `compute_satellite_state()`（含 ECEF 位置/速度），`geodesy.CoordinateConverter.ecef_to_llh()` 能把 ECEF 转经纬高；但没有任何地方把卫星画到地面地图上：`desktop/sat_track_panel.py` 只是过境列表（`SatTrackPanel`，provider 注入 `aos_unix/los_unix`），`desktop/rf_sky_view.py` 是天空视图（az/el），`desktop/constellation_panel.py` 是星座/天空视图。**全仓没有 `subpoint/ground_track/footprint` 符号。**

**QGIS 怎么做**：**它不做轨道计算**。QGIS 没有卫星传播器；这类功能靠插件（例如 QGIS 的卫星跟踪插件）自己算，再把结果作为 `QgsMapCanvasItem` 或临时矢量图层画到画布上。它能提供的是「画」的能力，不是「算」的能力。

**代价**：纯计算 + 绘制，**不需要新依赖**：
- 星下点：`ecef_to_llh(x,y,z)` 一次调用（注意 WGS72/WGS84 差异，见下）。
- 地面轨迹：按时间步长取 `compute_satellite_state()` 的 ECEF，转经纬，处理跨 180° 经线的折线断开。
- 覆盖圈：以星下点为中心、地心角 `acos(Re/(Re+h))` 为半径，用球面/椭球 direct 公式取 72 个方位点连成多边形。
- 绘制：`OsmMapView.add_layer("ground_track", painter_cb)`，与 ADS-B 图层同一种机制。

**不加会怎样**：用户只能看「方位/仰角/距离」数字和过境时间表，**看不到卫星现在在地球哪一侧、下一次过境从哪个方向来、覆盖圈盖住了哪里**。这恰好是 SDR/卫星接收用户最常问的三个问题。这是本清单里**唯一一项「加上去直接多出一个视图」**的能力。

**结论**：**最值得做，但实现路径不是抄 QGIS**——用我们已有的 SGP4 + Web Mercator + 叠加层，约 150–200 行。落地前要把椭球边界写清：`orbit.py:geodetic_to_ecef()` 是 **WGS-72**（第 192 行 docstring；第 14–15、47–51 行说明「与 sgp4 legacy 模式一致」），`geodesy.CoordinateConverter` 是 **WGS-84**（站址/GNSS）。做星下点时，SGP4 的 ECEF 必须用 WGS-72 反算，或整条链统一到同一族；**不要**把 WGS-72 的 ECEF 直接喂给 WGS-84 的 `ecef_to_llh()`，否则是米级系统差。`orbit.py` 的选择有明确理由，不要为了「统一」把它改成 WGS-84。

### 10.6 几何运算与空间索引

**我们现在**：没有多边形/点面关系/相交/缓冲区；ADS-B 距离用 haversine；星座可见性是对每颗星循环判断；没有空间索引（对象数量在几十到几百，暴力循环够用）。

**QGIS 怎么做**：`QgsGeometry`（`src/core/geometry/qgsgeometry.h`）的 `distance()/intersects()/contains()/closestSegmentWithContext()/buffer()/centroid()`，后端 GEOS；`QgsSpatialIndex`（`src/core/qgsspatialindex.h`）的 `insertFeature()/intersects(QgsRectangle)/nearestNeighbor(QgsPointXY, n, maxDistance)`，后端是 rtree/spatialindex。

**代价**：GEOS 是 C++ 重依赖（QGIS 用 `FindGEOS.cmake` 单独找）；Python 侧 `shapely` wheel 约 2–3 MB，API 与 QGIS 的 `QgsGeometry` 高度相似但更 Pythonic。

**不加会怎样**：做不了「卫星覆盖圈是否覆盖某区域」「飞机是否进入禁飞区」「两个覆盖圈是否重叠」这类判断；但对当前功能（列表、点绘制、距离）没有影响。

**结论**：**按需加，且加 shapely 而不是 GEOS/QGIS**。只有在产品明确要做地理围栏/区域覆盖分析时才引入；几百个点不需要空间索引，先暴力算，等数量级上万再说。

### 10.7 统一搜索（定位器）

**我们现在**：`desktop/command_palette.py` 只搜命令；`desktop/location_panel.py` 的城市搜索是面板内的 `_SearchWorker(QThread)` 调 Nominatim（`_do_search/_on_search_done`）；卫星、频率、录制的搜索各自散在对应面板。用户要先知道「去哪个面板搜」。

**QGIS 怎么做**：`QgsLocator`（`src/core/locator/qgslocator.h`）注册多个 `QgsLocatorFilter`（`qgslocatorfilter.h`）：`name()/displayName()/prefix()/priority()` 是查询接口，`fetchResults(string, context, feedback)` 异步执行并通过 `resultFetched()` 推送结果，`triggerResult()` 执行；`QgsLocatorWidget` 是统一输入框，结果按 `Priority`（Highest…Lowest）排序。过滤器覆盖工程图层、算法、设置、书签、地图服务等。

**代价**：低。接口 + 注册 + 异步 + 结果排序，约 200 行；不需要新依赖。

**不加会怎样**：用户找不到「输入 ISS 直接定位」「输入 145.8 跳到频率」「输入北京切站点」这种跨面板直达；功能都在，但发现成本高。

**结论**：**值得做**，但不要抄 `QgsLocator` 的 C++ 模型/线程；把 `command_palette` 升级为宿主，定义 `SearchProvider` 协议（`prefix/priority/search(query)->results/activate(result)`），先接三类：命令、地点（现有 Nominatim）、卫星。这比 QGIS 的实现小一个数量级，且复用已有异步 worker。

### 10.8 地理编码/逆地理编码

**我们现在**：`location_panel.py` 直接请求 Nominatim（`_SearchWorker`），有联网提示与断网降级；没有逆地理编码（点地图→地名），没有多provider 抽象。

**QGIS 怎么做**：`QgsGeocoderInterface`（`src/core/geocoding/qgsgeocoder.h`）定义 `Flag`（`GeocodesStrings/GeocodesFeatures`）、`geocodeString()`、`geocodeFeature()`、`flags()`；`QgsNominatimGeocoder` 是一个实现；`QgsGeocoderLocatorFilter` 把地理编码接进定位器。**3.44 核心没有逆地理编码接口**（全树搜不到 `reverseGeocode`），QGIS 也只做正向。

**代价**：我们已经有能用的实现；抽象只在「换 provider / 逆地理」时才有价值。

**不加会怎样**：点地图任意位置看不到地名；换 provider 要改面板代码。都不是核心痛点。

**结论**：**不抄**。若做 10.7，把现有 Nominatim 调用包成一个 `SearchProvider` 就够了；逆地理等有明确需求再加。

### 10.9 地图量算工具

**我们现在**：**没有**。地图上不能拉尺量距离/方位；ADS-B 表格有距离列，但那是逐行计算，不是交互量算。

**QGIS 怎么做**：`QgsMapTool`（`src/gui/maptools/qgsmaptool.h`）的 `canvasPressEvent/canvasMoveEvent/canvasReleaseEvent/activate/deactivate` 是交互状态机基类；`QgsMeasureTool`（`src/app/qgsmeasuretool.cpp`）+ `QgsMeasureDialog` 实现「点击加点、实时显示段长/总长/方位」；距离计算走 `QgsDistanceArea`。

**代价**：`OsmMapView` 里加一个模式（约 100 行鼠标状态机 + rubber band 绘制）+ 10.2 的椭球距离/方位（几十行）。不需要 QGIS 的 map tool 框架。

**不加会怎样**：用户不能在图上量「本站到目标多少公里、方位多少」，只能靠外部工具；对天线指向/覆盖检查是一个实际缺失。

**结论**：**值得做小版本**：右键菜单「量算」，两点显示大地线距离 + 初始方位 + 终点方位，多点显示总长。不要引入 `QgsMapTool` 体系。

### 10.10 工程/数据持久化

**我们现在**：`desktop/settings.py`（应用设置）、`desktop/layout_store.py`（布局）、书签、录制索引，各自 JSON；没有「工程文件」概念，也没有图层清单。

**QGIS 怎么做**：`QgsProject`（`src/core/project/qgsproject.h`）的 `read()/write()` 把图层树、CRS、样式、数据源 URI 序列化为 `.qgs`（XML）或 `.qgz`（zip）；`layerStore()/layerTreeRoot()/crs()` 是运行期模型；读失败返回错误列表并由坏图层处理器接管。

**代价**：高，且与领域模型不匹配。我们的「工作区」是「设备 + 频率 + 面板布局 + 解码参数」，不是「图层集合」。

**不加会怎样**：不能把「一整套图层」发给同事；但我们的用户分享的是录制文件、TLE、配置，不是 GIS 工程。

**结论**：**不抄**。等价物是布局预设 + 书签 + 录制索引；保持分开比塞进一个 `.qgs` 式文件更清楚。

## 11. 明确不建议加

这一节是给后来人看的「别以为漏了」。QGIS 是通用 GIS 平台，下列设计对 SDR/卫星接收应用是纯负担。

| 不抄的东西 | QGIS 位置 | 为什么对我们不成立 |
| --- | --- | --- |
| 通用符号化/渲染体系（符号层、渲染器、数据定义属性、表达式驱动样式） | `src/core/symbology`（`QgsSymbolLayerRegistry`、`QgsFeatureRenderer`、`QgsSymbolLayerAbstractMetadata`） | 我们的「符号」只有点、折线、圆、文字四类，`QPainter` 回调几十行就够。引入符号层模型要维护「符号类型注册 + 属性 schema + 表达式绑定 + 单位/比例尺」，收益为零 |
| 完整投影引擎与 CRS 数据库 | `src/core/proj` + PROJ + `resources/srs6.db` | 输入全是 WGS84；GCJ-02 连 PROJ 都不解决。为「可能导入地方坐标」背 10 MB 数据和一套轴序/单位语义，不划算（10.1） |
| 属性表、要素编辑、编辑事务与撤销栈 | `src/core/vector/qgsvectorlayer.cpp`、`QgsVectorLayerEditBuffer`、`src/gui/attributetable` | 我们编辑的是「站址、频率、设备参数」，不是「要素属性」。事务/撤销/字段约束是为 GIS 数据生产设计的，套过来会扭曲现有设置模型 |
| 图层树与工程文件（`.qgs/.qgz`） | `src/core/layertree`、`src/core/project/qgsproject.cpp` | 工作区是「设备 + 频率 + 面板 + 解码参数」，不是图层集合（10.10）。图层树模型/视图还会带来拖拽、图例、可见性继承等一大堆 UI 规则 |
| 表达式引擎（bison/flex 语法 + 函数库 + 上下文） | `src/core/expression`（`QgsExpression`、`QgsExpressionContext`） | 我们的计算用 Python；再引入一门表达式语言意味着解析器、函数注册、类型转换、错误定位、沙箱。只有「用户自定义派生字段」这类需求才值得 |
| 3D 地球仪（Qt3D 场景） | `src/3d`（`Qgs3DMapScene`、Qt3D 依赖） | 依赖重、与 Widgets 体系并行；我们的「地球」用 Web Mercator 2D 图 + 星下点/轨迹已足够。真要看三维，一张纹理球比 Qt3D 便宜 |
| Processing 框架、算法提供者、模型器、批处理 | `src/analysis`、`src/core/processing`、`python/plugins/processing` | 我们没有被 GIS 算法编排的需求；现有 DSP 流程是实时流，不是批处理 DAG |
| Server / Quick / 点云 / 网格 / 矢量瓦片 / STAC | `src/server`、`src/quickgui`、`pointcloud/`、`mesh/`、`vectortile/`、`stac/` | 与桌面 SDR 接收无关；每一样都是独立产品面 |
| 插件下载安装器与插件仓库 | `python/pyplugin_installer` | 没有第三方生态；开放下载 = 供应链与崩溃隔离风险。内部扩展用静态注册即可（第 7 章） |
| 认证框架（`QgsAuthManager`、OAuth2、证书库） | `src/core/auth` | 我们的远端依赖是 TLE/SOTA/地图瓦片，API key/匿名访问足够；证书库是给企业 GIS 服务用的 |
| 地图排版/打印（Layout、Composer、Atlas） | `src/core/layout`、`src/gui/layout` | 我们不出纸质地图；截图/导出 PNG 用 `QWidget.grab()` 就够 |
| `QgsSettings` 的 QSettings/INI 存储层 | `src/core/settings/qgssettings.*` | 我们的 JSON + schema 在可读性、可测性、损坏恢复上更好；只借「用户显式设置过」与「管理员默认」两个概念（第 4 章） |
| 完整定位器框架（C++ 模型/过滤器/异步） | `src/core/locator` | 借「统一搜索」的概念即可，不需要它的模型/视图/线程实现（10.7） |
| 坏图层 XML 数据源修复模型 | `src/app/qgshandlebadlayers.*` | 借「在候选目录里自动找文件」的交互即可，不需要 XML 数据源协议（第 6 章） |

一条通用判据：**QGIS 的每个子系统都在解决「任意数据、任意来源、任意用户」的通用性问题**。我们的输入是确定的（SDR 设备、WGS84、自家格式），通用性带来的抽象成本没有对应的收益。凡是要「为未知的第三方数据/插件/格式」做设计的部分，默认不抄。

## 12. 对照总表与落地顺序

### 12.1 已用另一种方式解决（不要重做）

| 能力 | QGIS 的做法 | 我们的做法 | 结论 |
| --- | --- | --- | --- |
| 地图底图 | `QgsMapCanvas` + XYZ 图层 + 图层树 | `osm_map.OsmMapView` 自绘 + 回调叠加层 | 等价，保留我们的 |
| 天球投影 | PROJ/CRS（地面） | `celestial_geometry` 四种天球投影 | 领域不同，保留 |
| 设置 | `QgsSettings` + 类型化条目 + INI | JSON + `config_schema` + 校验理由 | 我们用得更合适 |
| 面板登记 | 插件 `initGui` + `addDockWidget` | `panel_registry.PanelSpec` 声明式 | 我们更集中，缺工厂（见 12.3） |
| 布局持久化 | `saveState()` 二进制 + 默认 blob | `layout_store` 结构化 JSON + 预设 | 我们更可读，保留 |
| 翻译 | `qgis_*.qm` + `qt_*.qm` | `l10n.py` + `desktop_*.qm` | 同构，缺 qtbase（见 12.3） |
| 主题 | 主题目录 + `style.qss` 变量替换 | 令牌 → QSS 生成 | 我们更可控，保留 |
| 错误处置 | 文案 + message bar | `error_catalog` + remedy 链接 | 我们更可执行，缺非模态呈现 |
| 资源分发 | 目录拷贝 + 少量 qrc | PyInstaller `datas` + CMake install | 形态不同，保留 |
| 打包 | CPack + 外部 OSGeo4W | PyInstaller + `deploy_runtime.cmake` | 我们的更贴近交付 |

### 12.2 本仓库自查发现的两个问题（与 QGIS 无关，但读代码时暴露）

1. **两个椭球族并存（有意的，不是缺陷，但容易误用）**：`mbdsdr_ai/orbit.py` 第 14–15、47–51 行明确选 WGS-72（与 sgp4 legacy 内核一致，避免混用引入米级系统差），`mbdsdr_ai/geodesy.py:CoordinateConverter` 用 WGS-84（站址/GNSS）。做星下点/覆盖圈时，SGP4 的 ECEF 必须用 WGS-72 反算，或与站址同族转换；把 WGS-72 ECEF 直接传给 WGS-84 的 `ecef_to_llh()` 会产生米级偏差且不会报错。**不要「统一成一个椭球」**——orbit.py 的选择有理由；要做的是显式选边并加对照测试。
2. **近名易混的两个入口**：`orbit.geodetic_to_ecef()`（WGS-72、km）与 `CoordinateConverter.llh_to_ecef()`（WGS-84、m）名字相近、语义不同，默认单位也不同。建议在函数名或 docstring 首行强制写明椭球与单位（例如 `wgs72_geodetic_to_ecef_km` / `llh_to_ecef_m`），不要在两者之间互相转发而不写清语义。

### 12.3 建议落地顺序

按「用户能否多做成一件事 / 成本 / 是否阻塞其他项」排：

| 优先级 | 事项 | 成本 | 用户获得 | 验收判据 |
| --- | --- | --- | --- | --- |
| P0 | 显式化 WGS-72/WGS-84 边界：重命名同名入口、写清星下点用哪套、加对照测试 | 小（改名 + docstring + 测试） | 避免星下点/覆盖圈在米级上「看起来对但不一致」 | 同一站址/卫星输入，两条链的经纬高差有明确上界并被测试固定；代码里不再有裸 `geodetic_to_ecef` 调用 |
| P1 | 星下点 + 地面轨迹 + 覆盖圈叠加到 `OsmMapView` | 中（150–200 行，无新依赖） | **多出一个「卫星在地球哪」的视图** | 选一颗 TLE，任意时刻星下点与外部工具误差 < 0.1°；轨迹跨 180° 不断线；覆盖圈闭合 |
| P1 | 非模态通知条（错误/进度/可带动作），由 `error_catalog` 决定是否打扰 | 小（一个控件 + 通知 API + 批量抑制） | 采集时不再被模态框打断；错误可堆叠 | 有 remedy 的错误出现按钮；无 remedy 的只进日志；批量导入只汇总一次 |
| P1 | 统一搜索：`command_palette` 接 `SearchProvider`（命令/地点/卫星） | 小（约 200 行） | 输入 ISS/北京/频率直达 | 输入前缀能过滤；异步结果不阻塞 UI；断网时地点 provider 降级不报错 |
| P2 | 椭球距离/方位（`geographiclib` 或 Vincenty）+ 地图量算模式 | 小–中 | 距离不再差几公里；可在地图上拉尺 | 与 QGIS/在线工具对照 1000 km 误差 < 1 m；跨 180° 正确 |
| P2 | 加载 `qtbase_<locale>.qm` | 很小 | 中日文界面里 Qt 自带按钮不再中英混排 | 切到 ja 后 `QMessageBox` 的 OK/Cancel 为日文 |
| P2 | `PanelSpec` 加 `factory`，面板由注册表构造 | 小 | 新增面板只改一处；为后续可插拔铺路 | 删除 `MainWindow` 中的硬编码构造后，全部面板仍能出现/恢复布局 |
| P2 | 设置项「用户显式设置过」标记 + `defaults_override.json` | 小 | 改默认值不误伤老用户；现场可统一默认 | 未设置项跟随新默认；显式设置项保持不变；覆盖文件优先级可测 |
| P3 | `JobRegistry` + 设备断开统一取消 | 中 | 状态栏能看到「正在跑什么」；断设备不再残留任务 | 注入断开事件后所有依赖 job 进入 canceled；无任务泄漏 |
| 不做 | 第 11 章全部 | — | — | — |

P1 的三项互不依赖，可以并行；P2 的「椭球距离」是「量算」的前置。P0 必须先于 P1 的星下点。
