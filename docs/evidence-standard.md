# 真机证据判据（Evidence Standard）

> 适用对象：`docs/**/*.md` 与 `experiments/**/README.md` 里所有**带数字的结论**。
> 一句话：**没有原始件的结论不许留在正文里当事实用；不能复跑的，必须写时点与原因。**
>
> 工具：`scripts/audit_evidence.py`（本判据的可执行版本）。文档是规范，脚本是闸门。

## 1. 四级定义

| 级别 | 名称 | 定义 | 必须提供什么 | 能否当“当前事实”引用 |
| --- | --- | --- | --- | --- |
| **E1** | 有原始件（measured-archive） | 结论可由**入库的原始测量件**离线复算 | ① 原始件路径（`.json/.csv/.rgb/.sigmf-data/.log/.bmp/.wav/.bin` 等，非 `.md`）；② 采集条件（设备型号、固件/驱动、端口、日期）；③ SHA256 钉扎（或等价的内容哈希）；④ 复算脚本/命令与容差 | 能，且必须同时给路径与采集条件 |
| **E2** | 可复跑（rerunnable） | 无原始件，但仓内有**确定性命令/测试**能当场重算出同一数字 | ① 精确命令（`python …` / `pytest …` / `ctest …`）；② 期望值与容差；③ 最近一次通过记录（CI 或本地输出） | 能，但须注明“由命令复跑得出，非存档” |
| **E3** | 不可复跑（non-rerunnable） | 当时有证据，但原始件未入库或硬件/网络已不在 | ① 时点（`YYYY-MM-DD`）；② 证据形态（截图/日志片段/会话记录/commit）；③ **当前不可复跑的具体原因**（无硬件、无过境、外部服务变更等）；④ 要恢复可复跑还缺什么 | **不能**当“当前事实”引用；只能作历史线索，引用时带“当时有证据、现不可复跑” |
| **E4** | 未验证（unverified） | 没有任何可核对证据，或证据与结论矛盾 | ① 显式 `未验证` 标记；② 原因码；③ 需要什么数据/设备才能定 | **不能**；不得写成“已验证/实测通过” |

### 原因码（写进标记里，便于脚本与人工同口径）

| 码 | 含义 |
| --- | --- |
| `no-artifact` | 只有文档自述，无原始件 |
| `synthetic-only` | 只有合成 fixture/假后端自测，不构成外部验证 |
| `hardware-absent` | 本轮无设备（VNA/SDR/rotator/声卡） |
| `network-absent` | 需要外网/授权，本轮不可达 |
| `time-point-only` | 只有历史时点产物（如 `.tmp-tool-results`），当前不可复跑 |
| `contradicted` | 存档数据与结论直接矛盾（不是“没测”，是“测了不支持”） |
| `partial` | 结论的一部分有证据、另一部分没有（须逐项标明） |

## 2. 硬规则

1. **正文里的每个测量数字都要能落到 E1–E4 之一。** 落不到就是 `E4/no-artifact`。
2. **E4 不得写成事实。** 禁止“已验证/实测通过/真机验证”等字样；改为“未验证（原因码）+ 复跑条件”。
3. **E3 不得冒充 E1/E2。** 历史 `results.json`、旧聊天记录、截图缩略图只能作历史线索；必须写清时点与当前不可复跑原因。
4. **E1 的原始件不得被后续覆盖。** 替换采集件必须同步更新 SHA256 与采集记录；测试里用 SHA256 钉扎。
5. **合成信号永远不是外部证据。** 用仓库自己的编码器造 IQ、用假后端跑链路，一律 `synthetic-only`，不得标 `measured-archive`。
6. **一个证据不能给一串数字背书。** 同一段落的多个数字要逐个核对；只给其中一个找到原始件，其余降级。
   **表格口径（2026-11-12 裁定）**：一条表格数字的证据锚点只能落在**同一行**、**表头行**、或**紧邻表标题行**
   （表格上一行）；其他数据单元格里的路径/命令**不给整表背书**。表头写「实测」只决定「这张表要不要按测量断言审」，
   不构成任何一行的证据。
7. **文档互相引用不算证据。** “见某某文档”最多是线索；两个文档写同一句话仍可能是同一次未留证的传闻。
8. **宁可降级，不要删除。** 保留结论与降级理由，方便以后拿到数据再升级。
9. **证据原件的扩展名必须落在可入库白名单内，提交后要 `git ls-files` 确认原件真的在版本里。**
   证据件先过 `.gitignore`：`docs/evidence/**` 由 `.gitignore` 的 `!docs/evidence/**`
   显式放行（该行必须排在 `*.log` 之后）；该目录之外一律按 `*.log` 等规则拦。
   新增扩展名前先 `git check-ignore -v --no-index <路径>` 验证，被拦就换扩展名或补规则。
   **只看 `git add` 没报错不算数**——`2026-11-06` 一份采样率读回原件因 `*.log` 被静默
   跳过，出现“台账入库、原件不在版本里”，最后改名 `.txt` 补交（原件 `c438904c` —
   `docs/evidence/sample-rate-readback-20261106-0305.txt:2` — `RTL-SDR 真机`）。提交后必须
   `git ls-files docs/evidence` 复核，原件不在列表里就是不合规。
10. **性能数必须带「同机并发负载」标记。**（本轮实例与复跑入口：
    `docs/perf-evidence/2026-11-11/ctor_segments_load.json`，
    `python scripts/repro/2026-11-11-ctor-segments-with-load.py --run N`）
    这台机器今晚常有十几条线并行，CPU 竞争能让同一入口的同一指标差 40–75%
    （本轮构造期实测到 2.2×）。
    - 墙钟/耗时结论必须同时记录：测量**前后各一次**的系统 CPU 总占用、本机
      python 进程数与各自 CPU 占比。缺这份记录的墙钟数只能作「本轮内相对比较」，
      **不得跨轮比较**，也不得据此写「A 比 B 慢」。
    - 同机两次测量差超过三成时，先按负载分组再比；分组后仍超三成才判「冲突」。
    - 本轮实例：同一 `MainWindow()` 构造期在高负载组与低负载组相差 2.2×，低负载组
      的读数与另一条线报的值几乎相同；逐次读数、系统 CPU 与本机 python 进程占比见
      `docs/perf-evidence/2026-11-11/ctor_segments_load.json`，复跑命令
      `python scripts/repro/2026-11-11-ctor-segments-with-load.py --run N`。
    - **量具自己付掉的开销必须声明在窗口内还是窗口外。** 计时脚本的
      prelude（枚举字体族、`QFontMetrics` 预热、`QApplication` 创建、import 等）
      如果发生在起计时点之后、被计指标之前，它既不属于产品耗时、又已经吃掉了
      产品本来要付的钱，必须写明「在窗口外」并单列其耗时；否则该指标被低估。
      实例（2026-11-12）：`first-tick-definitions.py` 的
      `QFontDatabase.families()` + `QFontMetrics(app.font()).height()` 跑在
      `T0` 之后、`t_ctor` 之前，中位 428.1 ms（408.0–470.5；另一轮 408.9），
      而报出的 `entry_to_tick_ms = ctor_ms + tick_ms` 不含它；同结构去掉 prelude
      的对照中位 1364.1 vs 933.8，差 430.3 ms（另一轮 455.3）。逐时间戳见
      `docs/perf-evidence/2026-11-12/prelude-window.json`，复跑
      `python scripts/repro/2026-11-12-prelude-window-probe.py --runs 3`。
11. **脚本自带的判据不等于我们的验收判据。** 引用任何脚本打印的
    OK / FAIL / 未复现 之前，先按验收判据手算一遍：脚本内置阈值是它自己的口径，
    脚本通过 ≠ 验收通过（例：首拍脚本内置的通过线比验收线宽，引用时必须换成
    验收线重判，不能直接抄它的结论行）。
12. **代码注释不是证据。** 注释里描述的机制（谁先死、谁持有谁、哪个对象无父、
    GC 何时收）在写进结论之前必须用探针验证一次，至少覆盖：`shiboken6.isValid(...)`、
    `parent()`（或 `QObject.parent()`/`owners`）、以及 `gc.collect()` **前后各取一次**；
    涉及「包装/C++ 谁先死」的还要取弱引用存活状态与删除后的 `isValid`。
    注释与探针矛盾时：**注释降级为历史线索，保留原文并标「已否证（日期/提交）」，
    不删**；结论只写探针能复现的那条。
    反例（2026-11-12）：`_return_panel` 注释称「C++ `QVBoxLayout` 比 Python 包装先走」，
    实测三个归位变体 `isValid=False` 事件 0 条；`spectrum_widget.py` 的
    `setLayout(…)` 被描述为「旧布局无父、靠 GC」，实测 `parent() == toolbar`、
    包装 gc 后仍活、C++ 删除后 `isValid` 正确转 `False`。两处都已按「已否证」入案，
    而非按注释下结论。
13. **用户的真实环境状态不是实验对象。** 实验前必须把 `HOME` / `APPDATA` /
    `QSettings` 存储 / `QSettings` 路径全部重定向到临时位置；隔离装置本身要有反证
    （先写「坏」值，证明不隔离必红、隔离后稳定）。
    **不得已触碰真实状态时，还原必须给哈希或类型级证据，不接受「我已还原」的自述**；
    备份原件在实验结束前不得删除，删除即视为放弃内容级证明。判据：
    - 「已还原」不算证据；要给「实验前抓到的 blob 哈希」与「还原后读出 blob 哈希」
      是否相等，或至少给读回类型 + 解码后的值；
    - `restoreState() == True` 只证明能解析，**不证明内容对**，不得替代哈希；
    - 备份件已删、无法回溯时，如实写「内容一致性不可证明」，不得用间接可解析性顶替。
    实例（2026-11-12，本轮 QSettings 隔离提交 `8ecf720f`）：
    - `HKCU\Software\MBDSDR\Desktop` 的 `three_column_sizes`：隔离实验中毒写后还原，
      第一次用 PowerShell 直接写裸 blob，Qt 6 在注册表里的 `QByteArray` 是带包装的
      REG_BINARY 形态，裸字节被读成 `str`，用户上次三栏布局失效（读回 35 字节的
      `bytes()` 转换直接抛 `TypeError`）。改用 `QSettings.setValue(..., QByteArray(...))`
      才恢复类型。备份 JSON 在收尾清理时被删，**内容一致性不可证明**（只剩会话日志里的
      还原后读回哈希 `c913f29c…` 与解码值 `[260,2000,326]`）。
    - `~/.mbdsdr/gui_config.json`：用 PowerShell `Set-Content -Encoding UTF8` 直写，
      PS 5.1 带 BOM，应用判为损坏文件并改名备份，用户观测站/窗口配置从原文件消失。
      记录见 `tests/test_ui_hard_defects.py` 的 docstring（「不要用 PowerShell 直接改
      这个 JSON」）。该次未留 commit 号，只作历史线索（E3）。
    后果写清：前者让 `QByteArray` 被读成 `str`、静默丢弃用户布局；后者让应用读不到配置
    并触发损坏备份分支——两者都不是「测试里的小事」，是用户可见的数据损失。
14. **量主题切换 / 全树重抛光必须关闭硬件自动枚举（`MBDSDR_OFFLINE=1`）。**
    规则 10 管的是同机并发负载，本条管的是**被量进程自己引入的硬件副作用**：
    `MainWindow` 构造期 `_auto_enum_worker` 会自动枚举并连接板载 SDR，随后的
    IQ 轮询把事件插进 `processEvents()`；主题切换正好在 `processEvents()` 前后
    计时，于是设备事件被算成「切主题代价」。判据：
    - 读数里出现与主题无关的秒级尖峰，且紧随其后有控件级 `setStyleSheet`
      突增 → 先查是不是被自动连接了设备，不要先怀疑主题路径；
    - 同一序列必须在 `MBDSDR_OFFLINE=1` 下复跑一次，**净成本以离线那轮为准**；
    - 设备事件不得写成「切主题耗时」，也不得据此判性能回归。
    实例（2026-11-12，触控模式连切 20 次主题）：未设 `MBDSDR_OFFLINE` 的两轮
    分别出现 27956.5 ms / 14132.0 ms 尖峰，伴随控件级 `setStyleSheet` 94 / 108 次；
    离线重跑同序列极差 142–210 ms、中位 153.5 ms、应用级 `setStyleSheet` 0 次、
    `repolish` 150.8 ms/次（占墙钟 98%）。回归用例
    `tests/test_theme_qss_growth.py`（模块顶部显式 setdefault 该变量）。
15. **端到端性能数字必须带运行条件，且不同负载下的读数不得并列成前后对照。**
    条件三件套：**逻辑核数、测量时系统 CPU 总占用、被量进程自身占核**（都取本轮
    实测；缺一条就不得写成绝对值结论）。同一指标在不同负载组之间的差值，**不得**
    写成「优化前 / 优化后」或「A 比 B 快」；要么按负载分组后组内比，要么只报
    「区间 + 条件」。反例（2026-11-12）：`docs/learn/dsp-performance-baseline.md`
    §5 曾把 3.75 → 6.83 MS/s 记成优化收益，实为高负载与低负载两次读数——旧码
    `06e42a69` 在低负载下同为 9.54 MS/s，且两侧 bench 脚本字节一致。
16. **「物理上不可能绿的断言」不许当断言。** 断言必须存在一个可成立的通过态；
    否则它只会长期挂红，把真正的新红淹掉，并让人习惯「反正它是红的」。
    写法：把不可能绿的部分降为**显式前置条件**（`assert` 里写明为什么它永远不会
    绿），真正要守的不变量换成**可修的子断言**。
    正例（2026-11-12，`tests/test_network_resource_leaks.py`
    `test_ring_reader_stop_timeout_keeps_thread_reference`）：read_fn 不被外部
    唤醒时线程不可能退出——「stop 返回后线程仍存活」只作前置条件；断言改为
    「join 超时后 `_thread` 引用仍保留」+「重复 `start()` 不出第二个生产者」，
    后者可通过补丁变绿，当前以 `xfail(strict=True)` 立案。
    反例：在 `stop()` 返回后直接写
    `assert not any(t.name == "mbdsdr-ring-producer" ...)`——线程物理上不可能
    退出，这条断言永远红，等于没有断言。

**§2 附则：skip 判据（2026-11-12 定，不另立编号）**

**skip 是「这台机器不具备条件」，不是「这条断言现在不成立」。** 两者混在一起，
被跳过的用例就变成长期假绿：CI 绿、本地也绿，但那条断言其实已经在红。

- **可以 skip**：拿不到硬件（无 RTL-SDR 枚举、无音频设备、无 GPS 串口、无 SatDump
  环境、屏幕宽度不足等），且 skip 消息必须写明**缺什么**；
- **必须红**：拿不到 id（`rtl_0` 之类标识符对不上）、接口契约变了、
  **本仓该有的依赖导不进来**。判断「该不该有」的口径：这份依赖是本仓自己的代码，
  还是本仓在 `requirements.txt` / `desktop/requirements.txt` 里声明要装的？
  任一为是 → 导入失败就是回归，不许 skip。

实例（2026-11-12）：`tests/test_no_sim_regression.py` 的 T3 原本对
`from desktop.main_window import MainWindow` 与 `MainWindow()` 各写了一句
`pytest.skip(f"依赖缺失: {e}")`。`MainWindow` 是本仓代码、PySide6 在
`desktop/requirements.txt` 里声明，两者都属「本仓该有」——已删掉 skip，
改成导入/实例化失败直接红。

附则的机械校验：硬件类 skip 的消息必须同时含 `缺：` / `可跑：` / `区分：`
三个标签（缺什么、怎么让它可跑、区分「没插」与「插了但打不开」），由
`tests/test_skip_message_contract.py` 按显式登记表逐条校验——只断言「消息非空」
不够，非空但含糊（「无设备」）正是要消掉的现状。

## 4. 工具口径（`scripts/audit_evidence.py`）

扫描对象：`docs/**/*.md` 与 `experiments/**/README.md` 的正文（跳过围栏代码块）。

### 4.0 入账口径（哪些数算“数字断言”，2026-11-12 写死）

- **带单位的数**：单位必须落在白名单内（`% dBm dBi dB MHz GHz kHz Hz ms µs us ns ppm km cm mm m mV V mA A mW W
  bps kbps Mbps Gbps bit bits 载波 帧 条 倍 次 ° Ω ohm`）；
- **无单位小数**：必须**同句有指标名**（RMS/SNR/BER/误差/回损/耗时/频率/增益/功率/噪声/相位/温度/电压/比例…）。
  **为什么**：否则 `0.25`、`98%` 这类排版数字、章节号、列表序号会淹没账本，真断言反而被埋掉；
- **行内反引号内容不入账**（`` `2.4MHz` ``、`` `path:N` ``、hash 都不算断言）。**为什么**：反引号里是代码/路径/标识符，
  不是这条文档在主张的测量值；把它计入会把“引用代码”误判成“声称测到了这个数”；
- **围栏代码块整段跳过**（同上理由）。因此「代码块里的数」在本闸门口径下**恒为 0**——不是“没有”，是“不算断言”。
- **规范文件里的「反例表」引用行不入账**：只限 `docs/evidence-standard.md` 中**表头首格为「反例」**的表格
  （§3 那张）——它引用的是“别人写错的原文”，不是本仓在主张的测量值。**为什么**：否则每加一条反例就往
  账本里塞一条假欠账，下一个人会以为又坏了。判定只看表头首格，不做关键词模糊匹配，脚本会把
  跳过的行数打印出来（「规范 §3 反例表引用行 N 条不计」），避免变成看不见的静默放行。

### 4.1 证据窗口（2026-11-12 裁定）

| 位置 | 窗口 | 说明 |
| --- | --- | --- |
| 散文 | 同一段 **±2 行** | 同段内的原始件路径/命令可以支撑该数字；跨段不算 |
| 表格 | **同一行 + 表头行 + 紧邻的表标题行** | 其他数据行里的路径不给整表背书（§2 第 6 条） |

窗口内命中下列之一才算“有证据”：

| 命中 | 判定 | 说明 |
| --- | --- | --- |
| 仓内存在的**非 `.md` 数据原件路径** | `有证据`（E1） | 路径须带白名单扩展名且在仓内存在；裸文件名、纯目录不算 |
| `.tmp-tool-results/**` 历史产物 | `有证据`（E3） | 时点线索，不能当“当前可复跑” |
| 可复跑命令（`python` / `pytest` / `ctest` / `make` / `scripts|tools/*.py`） | `有证据`（E2） | 命令里带仓内路径时要求路径存在 |
| `未验证` / `证据不足` / `待核实` 等标记 | `已显式标未验证` | 表格的“未验证”只写在表头/他行时，不给整表背书 |
| **只有 commit / 四元组** | **`无证据`** | 见 4.2 |

### 4.2 commit 与四元组都不是测量证据（2026-11-12 裁定）

- **commit 只能证明“某个时刻存在这段文字”，证不了“这个数字是测出来的”**，故只作 **E3 时点线索**，计 `无证据`。
  （旧版本节表格把 commit 列在“有证据”里，与 §3 反例表自相矛盾，已按 §3 改正。）
- **四元组（基准 hash + `path:N` + 字面量）是防漂移的坐标机制，不是防编造的证据机制。** 它回答
  “这句话是不是这次改动写的”，不回答“这个数是不是测出来的”。四元组齐备而原始件缺失，本闸门仍判 `无证据`。
- **源码 `path:line` 同样不算证据**：源码里有这个常量 ≠ 这个测量值来自那里。能作 E2 的只有
  **可复跑命令**，且命令本身要写在文档里。
- **例子（2026-11-12）**：能自洽的错误值，只有独立冻结的断言能拦——把阈值和人工卡同步改到同一个错数，
  拼装测试仍绿，只有单独冻结数值的断言会红。往返只证可逆、不证正确。

输出三栏：

| 栏 | 含义 |
| --- | --- |
| 有证据 | 命中原始文件 / 可复跑命令；括号内注明 `E1 有原始件` / `E2 可复跑` / `E3 不可复跑` |
| 无证据 | 什么都没命中，也没标未验证；**只命中 commit 或四元组的也在此栏** |
| 已显式标未验证 | 窗口内有 `未验证`/`证据不足`/`待核实` 等标记 |

退出码：**存在任意一条“无证据且未标未验证”即返回 1**；全部有证据或已标未验证返回 0。
可用 `python scripts/audit_evidence.py --paths <file>` 对单个文件做反证；`--json` 输出机器可读结果。

强规则：正文里带 **`实测` / `测得` / `约` / `≈`** 的数字一律入账，必须有原始件路径、
可复跑命令或就地 `未验证` 标记，否则报红。

表格标注口径：`未验证` 只写在表头或同表别行时，**不给整表背书**。本行若真带原始件按 E1 计；
否则仍记“已标未验证”，但说明栏写明“仅窗口内他行标未验证（本行无标注，需核）”。

### 4.3 三道闸门各管什么（互不覆盖）

| 闸门 | 管什么 | 判据 | 不能替谁 |
| --- | --- | --- | --- |
| `scripts/audit_evidence.py` | **数字级** | 每个测量数字能否落到 E1–E4 | 不能证明结论词本身为真 |
| `scripts/check_red_lifecycle.py` | **结论词级** | 完成态谓词有没有红榜处置与复跑命令 | 不能证明完成态句里的数字为真 |
| `scripts/verify_claims.py` | **引用漂移** | 四元组的 hash / `path:N` / 字面量是否仍成立 | 不能证明数字是测出来的（见 4.2） |

**三者互不覆盖，谁都不能替谁。** 三个都绿 ≠ 全仓无假断言：数字有证据而结论词在撒谎、结论词有处置而数字是编的、
四元组不漂而数值从未测过，都是本表允许存在的组合。

**测试这一层同理：测试名声称的行为，必须在用例里有对应断言，否则它就不是测试——收集器、冒烟、往返都不例外。**

### 7.5 裁定：对照表 / 状态列算不算断言（2026-11-06）

**裁定按列的性质二分类，不按词面一刀切：**

| 列的性质 | 判定 | 要求 |
|---|---|---|
| **A 位置/对照类**：回答「有没有、在哪、和谁对应」 | **不算修复断言** | 必须能点开代码位置（`path:line` 或符号）；不要求 hash；**禁止**写成完成态谓词 |
| **B 完成/量纲类**：回答「改没改好、收敛成什么值、何时生效」 | **算断言** | 必须四元组（hash + `path:line` + 字面量），否则按未证实红 |

**判据（三问，任一为"是"即归 B 类）**

1. 去掉该谓词后，读者还能不能只凭同行代码位置判断"两边是同一实现"？能 → A；不能 → B。
2. 同行有没有给出收敛后的**具体值/单位/行为**（如 `MS/s`、3 位小数、`-50→6 dB`）？有 → B。
3. 这一列会不会被用来回答"这个缺陷关了吗 / 能不能验收"？会 → B。

**理由**：断言闸要抓的是"没有证据的完成结论"，不是所有带结论色彩的词。A 类列本质是索引
（"这里和那里是同一条实现路径"），靠代码位置即可自证；强行要求 hash 会把索引逼成散文，
反而丢掉可点开的证据。B 类列一旦写成完成态，就是交付结论，必须留证——否则就是
"工具报通过 = 全仓无假断言"的那个洞。

**反例（同一句，两种判法）**

- A 类（不算）：`reference-mechanisms` 对照表的「对齐」列只写"两侧都读 `desktop/settings.py`"——
  这是位置索引，`path` 就够，**不要求** hash。
- B 类（算）：`parameter-unification.md` 那句「统一 `MS/s`、3 位小数（取证 `d0b585a0` …）」——
  它回答"显示口径收敛成什么值"，属完成/量纲结论；**去掉四元组就必须红**。
- 误判反例（会被当成 A 类放掉）：同一条「统一为 4 位小数」只写"见 `constants.py`"——
  读者会直接当作改完，属 B 类；只给路径不给 hash 仍判未证实。

**落地**：本轮先按本裁定改造两处文档——`reference-mechanisms` 的对照列改写成「实现位置：…」（A 类），
`parameter-unification` 的状态列按 B 类补四元组。扩词表后的新红仍超阈值（见 §7.3），故未开闸。

1. 真断言（完成态谓词 + `hash` + `path:line` + `字面量`）仍判 OK——不是把该词整体放掉；
2. 该否定句仍进扫描集并判 `NO_HASH`——不静默转绿，误报只能靠人工销。

试解析——真·全数字 commit 才能被识别，形如日期的纯数字串解析失败即按无 hash。

### 7.7 四元组行号的坐标口径（2026-11-06 写死）

**口径**：`path:N` 是**当前 HEAD 坐标**。新增的「行号内容校验」必须取
`git show HEAD:<path>` 的第 N 行，判断该行是否包含被引字面量；**不得取被引提交坐标**
（`git show <hash>:<path>` 第 N 行）来判。

**依据（8/8 反例，2026-11-06 实测）**：settings-inventory 那批 8 条四元组在 HEAD 坐标
全部成立，但在被引提交坐标全部不成立：

- `2614c7f8` 的 `desktop/config_schema.py:377` 当时是 `agc_enabled`
  （不是 `pass_min_elevation_deg`）；
- `6ed9ee7d` 的 `mbdsdr_ai/sdr_backend.py:111` 当时是空行
  （不是 `DEFAULT_SAMPLE_RATE_HZ = 2_400_000`）。

同一批四元组在两套坐标下会被判成相反结果，所以口径必须在校验实现前钉死。

**区间行号**：`path:N–M` 默认只取首行 N 判定；确需「区间内任一」语义时，必须在字面量后
显式写 `区间内任一`，否则按首行判。

**与现有三步的关系**：`verify_claims` 现三步只校验「该提交确实改过该路径、且
`git log -S` 能在同一 hash 命中该字面量」（`cat-file` / `--name-only` / `log -S`），
**不校验行号内容**；第 4 步（HEAD 第 N 行含字面量）就是补这一环，判红名为「行号失效」。

**第 4 步已实现（2026-11-11，`--check-lines`）**：`scripts/verify_claims.py`
的 `check_line()` 按本节口径取 `git show HEAD:<path>` 第 N 行；区间只判首行。
默认只报不拦；`--strict-lines` 是硬门（白名单清零后自动生效，见 §7.7.1）。

首跑分布（`--docs docs`，与前三步同批 74 条可证实断言）：**含字面量 39 / 行存在但不含 35 /
path 或行号不存在 0**。35 条集中在被后续重构推移过行号的文件（`settings-inventory` 12、
`reference-mechanisms` 6、`parameter-unification` 5）。

**首跑 35 条是口径缺陷，不是 35 个错（2026-11-11 裁定）**：HEAD 每前进一次行号就漂一次，
「行存在但不含」在文件被改过之后是**正常老化**。把这类直接当红灯，主闸门会随每次提交变红，
闸门立刻变成狼来了。故判定从三态扩成**四态**，用「坐标基准」把「写错」和「老化」分开：

| 态 | 条件 | 颜色 | 是否影响退出码 |
|---|---|---|---|
| `含字面量` | 第 N 行含字面量（先精确，再空白归一） | 绿 | 否 |
| `错引` | 行存在但不含，且基准**就是第 N 行的 blame 提交（或创建该行的提交）** | 红 | `--fail-on-line-misref` / `--strict-lines` |
| `需重定位` | 行存在但不含，但基准**不是**该行 blame（含基准过期、基准写成 HEAD、或根本没有基准） | 黄 | `--strict-lines`（白名单除外） |
| `path 或行号不存在` | 取不到第 N 行（sub：HEAD 无此路径 / 路径存在但行数不够） | 红 | `--strict-lines`（白名单除外） |

**坐标基准（baseline）＝该四元组所指那一行的债主**，即
`git blame -L N,N --porcelain HEAD -- <path>` 输出**首行首字段**的 40 位哈希
（该行最后一次改动的提交）。允许写「创建该行的提交」——只要该行此后没被改过，
两者就是同一个哈希；一旦被后人改过，创建者就已不是债主，基准随之过期 → 判黄重定位。

三种写法，优先级从高到低：

1. 同一行行尾：``（基准 `abc1234`）``；
2. 最近一个标题行里的同一写法（整段生效）；
3. 文首 20 行内：``<!-- line-baseline: abc1234 -->``（整篇生效）。

**判定方法**：不解出基准或基准解析不出 commit → 一律 `需重定位`（**不得判红**）；
能解出则取第 N 行的 blame 提交比对：

- 相同 → `错引`（红）：这一行从头到尾都归这笔提交负责，内容却对不上，说明坐标写错了；
- 不同 → `需重定位`（黄）：该行已被后来的提交改过（或基准根本不是这一行的债主），
  需要重新定位并把基准换成新的 blame 提交。

**为什么不用「基准之后该文件有没有提交」**：那个口径只能按文件粒度猜，且**随手把基准写成
当前 HEAD** 时，HEAD 永远不是该行的债主，于是错坐标会永久停在黄牌、永远转不成红——
闸门看着在跑，实际漏抓。改成 blame 口径后，「基准必须是债主」本身就是可判定的：
写 HEAD 的基准一定判黄，不会被追认合法。

**反证（写进 `tests/test_verify_claims.py`，必须长期绿）**：

1. 基准**故意写成当前 HEAD**、而该行由旧提交创建 → 必须判黄（不得判红，更不得判绿）；
2. 基准 == 该行 blame、但字面量不在该行，且该文件此后**另有提交** → 仍判红
   （旧口径会把它放过成黄）；
3. 基准取「创建该行的提交」，该行后来被改签名 → 判黄（基准已过期），不判红；
4. 有意错引样本（假 docs 目录 + 真实存在但内容不符的行）→ `--fail-on-line-misref`
   返回非零、输出出现「错引」；验完即删样本。

**输出**：分布表四行；`需重定位` 逐条列出 `文档:行 / hash / path:N / 上次基准 /
该文件此后几次改动 / 最近一次改动提交`；并附「按文件聚合」视图（按文档、按目标代码路径
两个维度），先看集中度再决定重定位怎么派活。

**老条目**：基准缺失的一律按 `需重定位`，随该文件下次改动时补基准，不补就不判红。
`17709482`（`hardcoded-parameters.md:756`）已查实为整行被 `4d5feff1` 删除，归
「断言已删」，不按漂移登记。

**写基准的顺序（2026-11-11 裁定）**：先重定位，再写基准，不许批量回填。
基准的作用是「从这里开始，行号再漂就是老化」；若在行号已经漂掉时就写当前 HEAD，
等于把错坐标一次性追认合法——此后文件不变、字面量也不在那行，只会判黄，闸门再也
抓不到它。这和「白名单先记账再放行」是同一个毛病。故：

1. 先在 `git show HEAD:<path>` 里搜字面量真实所在行，改 `path:N`；
2. 复跑 `--check-lines`，该条变成 `含字面量` 才允许写基准；
3. 基准取**该行的 blame 提交**（`git blame -L N,N --porcelain HEAD -- <path>` 首字段），
   **不得**取当前 HEAD，也**不得**取被引提交（被引提交是历史坐标，不是基准；
   二者相同只是巧合，不是取值依据）；
4. 写在同一断言行，形如「（基准 + 反引号包住的短 hash + ）」，不用文件级 `line-baseline` 一次性覆盖全篇——
   那会把同文件里尚未验证的断言一起放行。

**基准不是证据**：基准只是坐标元数据。`classify()` 选被引提交时，**非基准候选优先、
基准兜底**——既避免「基准写在证据 hash 之前被当成被引提交」（`_commit_touches` 必然不命中
→ 整条假 STALE），也不会误伤「证据与基准恰好是同一笔」（如单位统一那条，两者同为
`ff964183`）。

**首轮重定位实测（2026-11-11，按代码路径分批）**：`含字面量 39 → 71`，`需重定位 35 → 3`，

### 7.8 统计快照的生成方式（2026-11-06 写死）

**规则**：凡对外引用的「断言分布 / 文档统计」快照，必须用 `git archive <HEAD> <dir>` 生成，**禁止**用 `git ls-tree --name-only` 的文本输出自行拼装。违反时数字会静默偏小，且无法复现。

**实证一（少 16 条）**：`core.quotepath=true` 下 `git ls-tree -r --name-only HEAD docs` 把 `docs/PRD-现状对照.md` 输出为 `"docs/PRD-\347..."`（带引号的八进制转义）。按「以 `.md` 结尾且不含子目录」过滤时该行被静默跳过 → 顶层断言数 156 变成 140，差额正好是 `PRD-现状对照.md` 的 16 条（`e4810574` 实测）。

**实证二（多算 / 不可追）**：复用旧临时快照目录（未清空就再抽下一个 HEAD）会把上一轮文档残留带进来，产生重复计行。`b0a440e3` 曾被报成 164（同口径正确值 156），该临时目录已无工件可追，只能作废。

**复现式（唯一口径）**：

```text
git archive <HEAD> docs | tar -x -C <tmp>
git show <HEAD>:scripts/verify_claims.py > <tmp>/vc.py
python <tmp>/vc.py --root <repo> --docs <tmp>/docs
```

- 范围：`docs/*.md` 顶层、非递归（加 `--recursive` 是 412，不是同一口径）；
- `EXCLUDE_FILES={claim-waivers.md}`；`audit_r2` 是子目录，顶层本就不含；
- `CLAIM_RE` 与该 HEAD 提交版逐字一致；豁免条数不参与统计（校验器只整文件跳过 `claim-waivers.md`）；
- 校验器必须是**该 HEAD 的提交版**（`git show <HEAD>:scripts/verify_claims.py`），不得用工作区在途版。

**已核对的分布**（同口径重跑，引用时带哈希）：`b0a440e3` 156/58/12/86；`d731bdeb` 156/58/12/86；`e4810574` 156/63/12/81；`81cd345a` 156/63/13/80。旧值 `164/58/17/89`、`140/58/12/70` **作废**。

## 8. 提交归属：`safe_commit` 的声明快照能证明什么、不能证明什么（2026-11-13）

> 适用对象：用 `scripts/safe_commit.py --files` 提交共享文件的人。
> 一句话：**声明快照管的是「声明之后有没有变化」，不管「这几行是谁写的」。**

### 8.1 判据是时间窗，不是归属

`--declare`（或提交进程启动时刻）记录每个文件的内容指纹；提交前重算，**字节不同就拒绝**
（退出码 4），并逐行列出新增 / 消失的行、按 claim 台账推断可能属于谁。它证明的是
「提交内容 == 声明内容」，**不证明声明内容里的每一行都归你**。

### 8.2 它不覆盖什么（别用「已覆盖」含混过去）

| 场景 | 声明快照的行为 |
| --- | --- |
| 声明**之后**别人往同一文件写行 / 删行 | 拒绝（退出码 4），逐行列出 |
| 声明**之前**他线内容就已经躺在工作区 | **放行**，原样落库（已进快照） |
| 你 claim 期间别人写入、但发生在声明之前的行 | 不拒；它们在快照里 |
| 我**声明前**写好、还没提交的 §6.1 行被别人的提交带走 | 那笔看不到「这是谁的」；行随声明方落库 |
| 他线**声明之后**追加、我又用同一个豁免开关放行的行 | 放行；理由与带入内容可能对不上（`1a092cf8` 带走 `mbdsdr_ai/bookmark_manager.py` 的登记行） |
| 未被 `--files` 列到的未跟踪文件 | **碰不到** |

`052828d1` 把两个未被 claim 的新测试文件带走，是它们**被写进了 `--files`**，不是
工具多带；`8982b4f9` 卷进两行，是声明之后同文件被他线写入。两起都是「内容没丢、
归属记错」，按提交追溯会指到别人身上。

倒数第二行是第 2 行的角色对调：第 2 行是「我把别人声明前的行带走」，反过来就是
「别人把我声明前的行带走」。`152449c2` 的 §6.1 登记行就是这样落进了 `b10fe3f6`
（12:05:02，比我 12:05:42 的提交早 40 秒），那一行的「预计提交 hash」列从此永久
失准（它写着「本笔」，实际落在 `b10fe3f6`）。

处置只有记账：**不得靠猜补 hash**。事后无法证明「如果没被扫走，它本来会落在哪一笔」，
改写这一列等于伪造一条不存在的计划；正确写法是在记录里注明「该行由 `b10fe3f6`
带出，原计划笔 `152449c2`」。这条也没有可机械判定的判据：提交时区分不出「我的行
已被我上一笔带走」与「被别人的笔带走」，所以**不设拦截**；同文件并发本身不是错，
真要加也只按提示处理。

反向的另一半是「别人的行被带走」，已有一例可复跑：`1a092cf8`（12:20）提交证据
标准时，把 `判据存量收口/6ae85f56` 在 12:18 追加的 `mbdsdr_ai/bookmark_manager.py`
登记行一起带进了自己的 tree，现位于 `HEAD:docs/COORDINATION.md:2465`。本笔声明于
12:17:03，该行属于「声明之后才出现」，成因是当时**同一个** `--allow-foreign-changes`
既豁免 7 个空行块的原文比对误报、也放行了 ⑰ 的声明后漂移——说明尾段
`foreign-changes:` 如实记了 `+1 行`，理由串却只写空行误报，**理由与那一行不对应**。
该行的「预计提交 hash」同样永久失准；处置同上：**不猜补、不回改，只记账**。工具侧
已据此拆成 `--allow-foreign-drift`（⑰）与 `--allow-foreign-before-declare`（㉑），
两个理由不许共用。

同向还有一例当场发生（2026-11-14 12:36）：`294924e4` 在提交 guard-accounting 时，
把我 12:34 为第 2 件追加的 4 条 §6.1 登记行一并带走（现见
`HEAD:docs/COORDINATION.md:2482-2485`），而那 4 个文件的改动直到 `0f887673` 才落库。
同样只记账、不改那几行的「本笔」列。

### 8.3 人该怎么补

1. **提交前逐文件自问归属**：这笔里有没有不是我写的行？查 claim 台账
   （`python scripts/file_claim.py status`）与 §6.1 登记行；两者都没有记录，就按
   「无凭据」处理，不要猜。注意 §6.1 行的 owner 本身也是台账的投影，不能当
   第二份凭据（见 §9）。
2. **留自己的行、排别人的行，用行范围**：
   `--exclude-hunk docs/COORDINATION.md:2051-2053`（`-U0` **新侧**行号，可只排 hunk
   内的几行；含删除行的 hunk 只能整块声明）。被排除的每个 `+/-` 行都在 blob 里
   逐字比对，对不上就拒绝——不要为了能用工具去挪行、改时间序。
3. **确实要一起带走，用 `--allow-foreign-drift "<理由>"`（⑰ 声明后漂移）或
   `--allow-foreign-before-declare "<理由>"`（㉑ 声明前他线块）**：两个豁免各管
   一道闸，理由不许共用。理由与逐文件增删行数会写进提交说明的 `foreign-changes:`
   / `foreign-before-declare:` 段，事后可查。
4. **查不到凭据就写「无凭据」**：说明或记录里明写「这几行归属无凭据（原因：
   当时未记录 claim / 时间点不可复跑）」，按 E3 处理；**不许**写成「已验证归属」。
   宁可留一个诚实的空缺，不要造一份看起来完整的归属。
5. **只有弱提示，没有强保证**：`--files` 里路径无当前 owner 的 claim 记录时打印
   `[claim] 该路径无 claim 记录，请确认归属：<path>`；说明里一次都没提某文件时
   打印 `[message] 说明未提及：<path>`。两者都不拦、不参与退出码——归属是人的
   签字，工具只负责让「没签字」和「说明漏了」被看见。

## 9. 归属证据的等级：§6.1 的 owner 列是台账的投影（2026-11-13）

> 与 §8 是同一件事的两端：§8 管「声明之后内容有没有变」（内容证据），本节管
> 「表上的名字能不能当归属」（身份证据）。两节合起来只有一句：**工具能证明
> 时间窗与内容，不能证明 authorship。**

### 9.1 表上的 owner 只能是台账当时的抄写

`docs/COORDINATION.md` §6.1 的 owner 列不是独立签名。写行时
`scripts/append_coordination_row.py` 会校验 `--owner` **必须等于该路径活跃
claim 的 owner**（无活跃 claim 时只认 60 分钟内同 owner 的释放记录），不一致
直接拒绝。因此行里的名字是台账当时值的拷贝，不是第二份证据。

更早的台账（2026-11-13 20:41 之前）不记签发人：`file_claim.py` 只落
owner / pid / token，没有 `issued_by`、没有命令行、没有 session。所以
「§6.1 写着谁」只等于「台账当时记了谁」；台账本身也不知道当时是谁按的回车。

### 9.2 两条禁令（循环论证的两个方向）

1. **不得用 §6.1 行反推归属。** 行是台账的拷贝，拿拷贝证明原件等于没证明。
2. **不得用归属再解释 §6.1 行。** 「因为这条线占着，所以这行写它」是同一份
   台账在自我确认。两句话互为前提，结论为零。

### 9.3 已经用过的归属结论要逐档复核

凡「凭 §6.1 owner 认定归属」的结论，按证据等级重写，不许停在「已确认」：

| 档 | 手上有 | 写法 |
| --- | --- | --- |
| A | 命令行 / `issued_by` 记录能直接对应 | 「归属：<线>（凭据：…）」 |
| B | 只有时间窗 + 文件集与某笔提交吻合 | 「与 <线> 的 <sha> 时间窗吻合；命令级凭据缺失」 |
| C | 只有台账 owner | 降级为「台账当时记了谁」，不写「归属」 |

2026-11-13 20:41:49 那两条空白理由 claim 就是 B 档：窗口包住 `e326d9d2`
（20:42:13）、文件集正好是那笔的两个文件，但没有命令行与签发人记录。写成
「归属已确认」不成立；写成「与我的流程时间窗吻合、命令级凭据缺失」才是可复核的。

### 9.4 补签发记录之前，只能这样收尾

要回答「这几行是谁写的」，只有两条路：回去补 `issued_by` / 命令行一类的签发
记录，或在记录里如实写「无凭据」（§8.3 第 4 条）。在没有签发记录的时段里，
§6.1 行与台账 owner 都只能当「当时登记了谁」，不能当「谁干的」。

## 10. 带整份还是选行：两个前置条件（2026-11-13）

§8 管「声明之后内容有没有变」，§9 管「表上的名字能不能当归属」，本节管
「这一笔该带文件里的哪些字节」。三节是同一件事的三个面：**工具只能证明它
实际带走的字节和带走时的坐标；带多了、带少了，都不在证明范围里。**

### 10.1 判据（两条，缺一不可）

只有同时满足下面两条，才允许把**整份文件**放进本笔：

1. **文件是 append-only 的，且有守卫。** 判据不是「我觉得它只会追加」，而是
   仓库里存在对应守卫：`docs/COORDINATION.md` 对应
   `scripts/check_coordination_append_only.py`（pre-commit ⑤），守卫进场才算。
   其它文档、代码、配置一律不算。
2. **该文件当前没有他线在途 hunk。** 「在途」= 相对 HEAD 有改动、但不属于本笔
   要提交的内容（他线 claim 覆盖的改动，或落在本笔声明之外的改动）。有在途
   hunk 就必须用 `--exclude-hunk` 选行；整份带走等于把别人的改动一起落库。

两条都满足时，整份带走是安全的；任何一条不满足，就只能选行。选行时行号必须
配 `--declare`（⑳），行序服从文件里的实际行号，不按 `--files` 顺序重排。

### 10.2 禁止兜底

**不允许用「整份带走」作为选不中行时的默认兜底。** 选不中行 = 判据不成立，
正确动作是停下来把范围算清楚，或者拒绝提交；不是把整份文件塞进本笔。
`052828d1` 就是整份带走一个非 append-only 文件的形态：内容没错、归属全错。

### 10.3 与 §8/§9 的关系

§8 回答「声明后变了没有」，§9 回答「名字能不能当归属」，本节回答「这一笔该带
哪些字节」。三者的共同结论只有一句：**把不属于本笔的字节带进来，任何一层都
补不回来。** 判据写在这里，`scripts/safe_commit.py` 的模块文档只指路、不复述。

## 11. 裸 `git commit`：什么时候允许、归属怎么留（2026-11-14）

> 起因：`claim-line` 生效后头 10 笔里有 2 笔缺口——`31afa759`（11:21:45，4 路径）
> 与 `423ac262`（11:22:04，2 路径），owner 同为 `无线电课清单线/6ae85f56`。
> 本节是这 2 笔的调查结论与由此定下的裸提交边界；**结论是个别线绕过，不是工具
> 漏了**，因此不逼所有线改道，只把「什么条件下可以不走 `safe_commit`」写死。

### 11.1 四种可能，逐条给证据

| # | 可能 | 结论 | 证据 |
| --- | --- | --- | --- |
| 1 | 没走 `safe_commit`（裸 `git commit`） | **成立** | 见 11.2 的三条 |
| 2 | 走了但身份与 owner 不逐字相等 | 不成立 | `scripts/claim_gate.py:387` 只在 `me == owner` 时放行；身份为空或不等一律 `blocked` 并写 `.locks/rejected.log`。同一线 11:08:38 对 `docs/learn/nanovna/vna-workflow.md` 的尝试就是 `identity=""` 被拒（自己持有也照拒）。这两个时点 `rejected.log` 无记录，说明身份就是台账原文 `无线电课清单线/6ae85f56` |

   `11588844` 才落库（`git blame -L 2331,2336`）。走工具就不可能不带行，带了就不可能
   在 `--name-status` 里消失。
2. **同一窗口工具是好的。** 规则生效后 14 笔里 12 笔有 `claim-line`，其中
   `5b0755b2`、`3e6ce34a` 写的是带会话后缀的完整 owner（`时空核对线/timeline-now`），

三条合起来：**钩子全程在跑、身份逐字正确、claim 全部活跃，唯独没有 `claim-line`**
——唯一解释是提交命令没经过 `safe_commit`，而该行只由它追加
（`scripts/safe_commit.py:969`）。

### 11.3 允许裸 `git commit` 的条件（四条全满足）

1. 本笔路径全部由本线**当前活跃 claim** 持有，且**没有他线在途 hunk**。有在途
   hunk 就要 `--exclude-hunk`，而它必须先 `--declare`（⑳，退出码 7）——这条路
   只能走 `safe_commit`。
2. 本笔要用的 **§6.1 行已在 HEAD**。行还躺在工作区时，只有 `safe_commit` 的 2c
   会把它带进本笔；裸提交会让它继续挂着（`423ac262`/`31afa759` 的 6 行就是这样被
   别的线顺手带走的）。
3. 本笔没有意图删除、没有 `--allow-foreign-drift` / `--allow-foreign-before-declare`
   这类需要留痕的例外。
4. 消息末尾**手写** `claim-line: <线名>`；owner 形如 `线名/会话短号` 时只写斜杠前
   的线名，与审计的归一口径一致（`scripts/claim_window.py` 的 `line_name`）。

裸提交仍然要过 pre-commit 五道闸，身份仍须 `MBDSDR_CLAIM_OWNER` 与台账 owner
**逐字相等**——「裸」只是不借助私有 index / 声明快照，不是绕过闸门。

### 11.4 裸提交怎么留下归属

- **行由人写，工具不代签。** `_claim_line_trailer` 只复述提交者此刻真实持有的
  claim（`scripts/safe_commit.py:942-997`）；没有 claim 就不写，「不写」本身是信号。
- **审计按行归线、按规则时点分段。** `scripts/audit_claim_lines.py`：生效前的
  「有 claim 无行」是正常空白，不计数；生效后的同样是**缺口**，单独计数，两段
  各用各的分母，不相加。
- **不能事后回填。** 历史提交不可变，缺口只计数、不改写；`--amend`/`rebase` 补行会
  换掉 SHA，让已有的审计引用全部失效——缺口的正确处置是记下来，不是美化。
- **裸提交没有内容级证据。** 没有声明快照、也没有私有消息副本，事后可复核的只有
  三样：claim 时间窗、提交文件集、消息里的 `claim-line`。按 §8 的口径，不得因此
  声称「归属已确认」。

### 11.6 反例（出现即不合规）

- 裸提交却要带共享文件、或把工作区的 §6.1 行留在外面——这时应走 `safe_commit`
  （2c 带行，⑰ 拦漂移）。

### 11.7 机检边界：`scripts/audit_bare_commits.py`（2026-11-14）

11.3 的四条前提写在文档里不等于被检查。裸提交没有工具位置（跑的就是
pre-commit，钩子里没有「这笔是裸提交」的标记），所以做成**事后区间审计**：

```
python scripts/audit_bare_commits.py                    # 规则生效以来
python scripts/audit_bare_commits.py --range A..B       # 指定区间
python scripts/audit_bare_commits.py --json --quiet     # 机器可读 / 只给计数
python scripts/audit_bare_commits.py --trend-report     # 按判据版本看比率
```

**只报告，不拦截，退出码恒 0。** 拦提交是 pre-commit 的事，这条入口的用途是
让缺口被看见，不是把提交挡在门外。

**覆盖范围先说清楚：本工具不判断某笔是不是裸提交。** 没有可机读的标记区分
裸提交与 `safe_commit`（私有 index、声明快照都不落库），所以「裸提交」这件事
本身在本工具覆盖范围之外；能机检的只有下面三项判据，另加一项提示（①后半）。

| 项 | 判据 | 实现 |
| --- | --- | --- |
| ① 文件集被本线活跃 claim 覆盖 | 按台账时间窗逐路径判断，**不看 §6.1 行**；消息里的 `claim-line` 用来认「本线」，写了他线的 claim 也算违规 | `audit_claim_lines.load_intervals` + `classify` |
| ①后半 他线在途（**提示，不是判据**） | 提交时刻同一路径是否正被他线持有；点名 sha/路径/持有者/时间差。**主数只算非登记面**，登记面窄锁单列 | `audit_bare_commits.check_foreign_hold` |
| ③ 只许追加的文件被删行 | 协调文档按 §6.1 表格行比较（剥离线末释放标记），删行/改写/整档删除都违规，**不管有没有 claim** | `check_coordination_append_only.removed_rows` |
| ④ 消息末尾手写 `claim-line` 且与台账一致 | 分桶复用审计脚本；规则生效前的「有 claim 无行」不计缺口 | `audit_claim_lines.classify` |

**①后半与 ① 必须分开读。** ① 问「本笔有没有被自己的 claim 覆盖」；①后半问
「本笔有没有踩在别人脚上」。两者互不替代：一笔可以既没有自己的 claim、又正好
压在他线的在途文件上，也可以各自单独成立。它**只报告不拦**——台账只能证明
「那个文件当时有人在改」，证明不了「带进来的是他那部分」。命中不等于被带入，
也可能双方都在改同一文件、各自只提交自己那段；所以措辞是「疑似」，只用来
触发人工复核，不计违规、不进 ① 的比率。判「本线」只认 `claim-line`；没有这行
的提交不猜，计入「无法判断」并交给 ④ 报缺行。

**①后半再拆两类，主数只算非登记面。** 登记面（协调文档）走 §6.1 窄锁：双方都
在往登记表写行、各自只提交自己那行，命中它是已知无害形态。2026-11-14 实测真实
区间跑出的 8 笔疑似 **100% 都是这一类**——提示如果命中全是同一个已知良性形态，
就等于没有信号（告警洪水等于没有告警）。所以报告先给：

- **主数**（非登记面文件）：疑似 n / 有 `claim-line` 的提交 d；是 0 就明写 0，
  并写「这项在当前实践下从未命中」——别让它读起来像一直在发现问题，也别当成
  清白的证明；
- **登记面窄锁**（已知形态，只做趋势）：计数与样本排在主数之后，不计入主数。

分母都用「有 `claim-line` 的提交数」。一笔同时踩到两类时两边各计一次，所以两类
之和可以大于分母；主数分母不剔掉登记面那些「可能命中」，否则它会随文档活动量
漂移。趋势里主数记 `suspected_foreign_hold.count`，窄锁记 `registry_count`。

以下明确**不覆盖**，输出里逐条打印「本项机检不覆盖，需人工复核」：

- 11.3-① 后半：他线在途 hunk 是否被带入（要 `--declare` 快照，历史提交没留）；
- 11.3-②：本笔要用的 §6.1 行是否已在 HEAD（哪几行「属于本笔」无法机读）；
- 11.3-③ 后半：`--allow-foreign-drift` / `--allow-foreign-before-declare` / 有意删除这类留痕例外。

两处例外要一并记住：协调文档自身在 ① 里**豁免**（它是登记面，走 §6.1 窄锁
写行，与 pre-commit 的 `self_key` 同一例外）；台账不存在时 ①/④ 报「未审计」，
不报「0 违规」——空白不是清白。

判据与反证：`tests/test_bare_commit_audit.py` 构造全满足 / 文件集不全 / 缺行 /
有删除四笔，必须分别落到 ①/④/③；把「缺行」改成合规，该测试必须红（已实测
两处断言变红）。本仓规则生效以来第一次跑（2026-11-14 11:37，HEAD=`ecbae6df`）：
① 1 笔（`87b3a36d` 的 `tests/test_goes_lrit_reassembly_stats.py`、
`tests/test_status_panel_reassembly_quality.py` 当时无 claim）、④ 2 笔（即 11.5
的两笔缺口）、③ 0 笔。① 的那笔是本次新发现的，不追溯改写，只记在这里。

这些数是**区间快照**，不是基线：同一入口在 `2790b483`（他线提交）之后又抓到
① 一笔（`docs/axioms.md`、`tools/axioms/current_stats.py`、
`tests/test_axioms_doc_current_stats.py` 当时无 claim）。数字随区间变，
复跑取当次输出。

**趋势**：每次跑都往 `<locks>/bare_commit_trend.jsonl` 追加一行（与
`coord_check_trend.jsonl` 同一放置、同一逐行 JSON 格式），记区间起止、总笔数、
①/③/④ 的违规数与**各自分母**、涉及线名去重数、判据版本；①后半的提示项单列
`suspected_foreign_hold`（自己的分母 = 有 `claim-line` 的提交数，不混进 ①）。
键 = 区间（首末提交 sha）+ 判据版本：同一区间重复跑只留一行；判据版本变了另起
一行。改了任一判据的行为必须升 `CRITERIA_BASE_VERSION`，否则两套口径会在趋势
里串成一段（v2 起含 foreign-hold；**v3 起 foreign-hold 拆主数/窄锁**，v2 的
`count` 混着登记面命中，两段不可比）。`--trend-report` 按判据版本分组，给每行的
「违规数/已审计数」，提示项给「主数 n/d」并另起一行给「登记面窄锁 m/d」；某段
主数合计为 0 时明写「这项在当前实践下从未命中」。

**比例怎么读**：违规笔数下降**不等于**实践变好——可能只是裸提交变少、提交总量
变少，分子自然小。所以趋势只给「该项违规数/该项已审计数」，不给总违规率；
汇总分母是各行分母之和，区间重叠会重复计入，只看方向；不同判据版本的两段
不可直接比较（判据放松也会让分子变小）。
