### 2.1 矩阵收敛：崩的是「主线程 `os._exit` + 窗口仍存活」这一格

脚本 `scripts/repro/2026-11-11-exit-os-exit-matrix.py`（提交 `d1f9f8b2`）。
每格 5 次，退出码全记；环境：profile 隔离到临时目录、`MBDSDR_OFFLINE=1`、
`QT_ENABLE_HIGHDPI_SCALING=0`。

```powershell
python scripts/repro/2026-11-11-exit-os-exit-matrix.py --suite exit --runs 5   # 8 格
python scripts/repro/2026-11-11-exit-os-exit-matrix.py --suite cond --runs 5   # 14 格
```

第一组（app × `os._exit` 调用线程 × 平台插件）：

| 单元格 | 退出码（5 次） | 崩/总 | `exec` 进 | `exec` 回 | `qt_live` |
| --- | --- | --- | --- | --- | --- |
| qapp / main / offscreen | 0,0,0,0,0 | 0/5 | 是 | 是 | 1 |
| qapp / main / windows | 0,0,0,0,0 | 0/5 | 是 | 是 | 1 |
| qapp / watchdog / offscreen | 0,0,0,0,0 | 0/5 | 是 | 是 | 1 |
| qapp / watchdog / windows | 0,0,0,0,0 | 0/5 | 是 | 是 | 1 |
| window / main / offscreen | 0xC0000005 ×5 | **5/5** | 是 | 是 | 1492 |
| window / main / windows | 0xC0000005 ×5 | **5/5** | 是 | 是 | 1492 |
| window / watchdog / offscreen | 0,0,0,0,0 | 0/5 | 是 | 是 | 1492 |
| window / watchdog / windows | 0,0,0,0,0 | 0/5 | 是 | 是 | 1492 |

第二组（`close()` 时序 + 设置线五个条件，均为 `window / main`，两平台各 5 次）：

| 条件 | offscreen | windows | 说明 |
| --- | --- | --- | --- |
| `plain`（不 close） | 5/5 崩 | 5/5 崩 | 基线：与第一组同格一致 |
| `close_before`（close + `processEvents`） | 5/5 崩 | 5/5 崩 | close 不改变该格 |
| `close_then_del`（close + `deleteLater` + `processEvents`） | 5/5 崩 | 5/5 崩 | 同上 |
| `second_window`（先建一套并销毁，再建第二套） | 5/5 崩 | 5/5 崩 | 第二套窗口不是变量（`qt_live` 2132） |
| `live_thread`（非 daemon 线程持 `QTimer`） | 4/5 崩 + 1 次 180 s 超时 | 5/5 崩 | 该线程不是变量 |
| `second_qapp`（同进程尝试第二套 `QApplication`） | 5/5 崩 | 5/5 崩 | 第二套没被 Qt 拒绝，也不是变量 |
| `kill_in_exec`（daemon 线程在 `app.exec()` 仍在跑时 `os._exit`，**设置线口径**） | 0/5 | 0/5 | 本机同口径同样不崩 |

收敛结论（只写观测到的判据）：

1. **崩溃条件是两条同时成立**：`MainWindow` 已构造并 `show()`（退出前
   `qt_live`≈1409–2132 个 `QObject` 活着）**且** `os._exit()` 由**主线程**
   在 `app.exec()` **返回之后**调用。只有 `QApplication`（`qt_live`=1）时不崩。
2. **不是 `os._exit` 本身**：同一进程、同样 1492 个存活 `QObject`，改由
   daemon 线程调 `os._exit` 即 0/5；`exec` 仍在跑时由 daemon 线程调也是 0/5。
3. **不是平台插件**：`offscreen` 与 `windows` 两列完全一致。
4. **不是 `close()` 时序**：`plain` / `close_before` / `close_then_del` 三格
   都是 5/5 崩；本线早前的 `window_del`（close + `deleteLater` +
   `processEvents` → `sys.exit`）另测 5/5 退出码 0。因此「`close()` 本身必崩」
   在本机不成立；close 只是不能救这一格。
5. **不是第二套 Qt 会话 / 非 daemon 线程**：`second_window`、`second_qapp`、
   `live_thread` 与 `plain` 同结果。
6. 同一格内 `0xC0000005` 与 `0xC0000409`（fail-fast）**交替出现**
   （如 `plain` offscreen：005,409,005,005,409）——退出期收尾不是单一错误码，
   单次退出码不能作为修复证据。
7. `live_thread` offscreen 第 3 次 180 s 超时且未打印 `RESULT`：记事实，不解释。

与设置线探针对账：它的 `hard` 变体是「`MainWindow` 存活 + `app.exec()` 仍在跑
+ daemon 看门狗线程 `os._exit`」，正落在本表 `kill_in_exec` 格（本机 0/5）与
`window / watchdog` 格（本机 0/5）。**两边不矛盾**：差异是「谁调 `os._exit`」
与「`exec` 是否已返回」，不是「`os._exit` 必崩」。

探针自身不是嫌疑人：本矩阵脚本不装 import 钩子、`atexit`、`faulthandler`、
异常钩子（`grep -n "atexit|faulthandler|__import__|excepthook|setprofile|importlib"` 仅命中注释一行），
收尾期不跑任何探针代码；上报用的 `RESULT` 行在 `os._exit` 之前 `flush`。

```
异常代码:    c0000005
错误偏移:    0x000000000001c91e
```

- 该偏移与 2026-11-05 00:11:19 用户可见弹窗**同一偏移**；本轮 `shiboken6+0x2fe08`

  具体函数**；不拿相邻导出反推。

### 2.5 `os._exit` 调用点分布 → 风险等级降级（2026-11-12 补）

全仓 `os._exit` 共 96 处 / 16 个文件（含本文件与本次取证脚本自身；
数字随本文增行会小幅上涨，此处为 2026-11-12 复核值）；**产品代码 0 处**
（`desktop/`、`mbdsdr_ai/`、`web/product/src/` 全部无匹配，`desktop/main.py` 也无）：

| 位置 | 处数 | 调用条件 |
| --- | --- | --- |
| `tests/conftest.py` | 5 | 仅测试会话收尾；Windows 分支先 `TerminateProcess`，`os._exit` 只是非 Win 兜底 |
| `web/product/tests/verify_build_json.py` | 3 | 测试脚本 |
| `scripts/ui_interaction_audit.py` | 1 | 审计脚本 |
| `scripts/repro/2026-11-11-*.py` | 35 | 本次取证脚本 |
| `docs/**` | 52 | 叙述文字 |

**降级结论**：产品运行期不存在 `os._exit` 调用点，用户可触发的路径里
**没有一处会走到这个崩溃**：

- 正常关窗 → 5/5 退出码 0；`Py_FinalizeEx`（格 F）5/5 退出码 0；
- 进程外强杀（任务管理器 / CI 看门狗）→ 用的是 `TerminateProcess`，
  不跑 DLL detach，本机 5/5 退出码 7（格 G），且 `tests/conftest.py`
  的注释独立记录了同一结论（「Windows 的 `os._exit` 仍走 DLL_PROCESS_DETACH…
  故 Windows 改用 `TerminateProcess` 硬杀」）；
- 只有**进程内主线程主动调 `os._exit`** 才 5/5–10/10 崩，而这在产品代码里
  一处都没有。

因此本条目从「用户可见闪退」**降级为「强制退出路径的收尾缺陷」**，
风险表按「开发者/脚本侧、用户不可达」记，不再占「用户可见缺陷」的位置。

### 2.6 `import rtlsdr` 与 `inspect.getsource` 的触发链（2026-11-12 补）

1. `list_devices()`（`mbdsdr_ai/sdr_backend.py:1723`）里的 `import rtlsdr`：
   **每次调用都执行该语句**，但只有本进程首次是真导入，之后命中 `sys.modules`；
   同函数内 `setup_rtlsdr_windows()` 每次都会跑（DLL 路径设置）。
2. `shibokensupport/feature.py:159 _mod_uses_pyside → inspect.getsource(mod)`
   **不是我们的代码，也不是废弃 API / 异常路径**，而是 PySide6 自己的导入钩子：

```
shibokensupport/signature/loader.py:72  feature_imported
  -> shibokensupport/feature.py:148     feature_imported
    -> shibokensupport/feature.py:159   _mod_uses_pyside
      -> inspect.getsource(mod)
```

   `import PySide6` 之后**任何模块的首次导入**都会走一次——打桩实测：
   `import rtlsdr` 期间对 `_io`、`os`、`warnings`、`__future__` 都各触发一次。
3. 对内存态模块该调用以 `OSError: could not get source code` 结束（已复现），
   **不致命**；代价是每次首次导入都 `linecache` → `tokenize.open` **读盘 + 分词**。
   崩溃栈正好停在 `tokenize.open`，就是"后台线程在退出瞬间还在读源码"。

**健壮性问题成立**（本次只登记、不改）：`enumerate_all_sdr_devices` 应在模块
导入期/启动期（主线程、UI 就绪前）完成 `import rtlsdr`，后台任务只做枚举，
避免在池线程里做首次重导入。

### 2.8 `ModulePanel` 内部结构二分（2026-11-12，阴性收口）

条件同 §2.7；每格 **20 次**独立子进程。Wilson 95% 区间按 `z=1.96` 计算。

| 格 | 形态 | 崩/总 | 比例 | Wilson 95% |
| --- | --- | --- | --- | --- |
| X（基线） | `ModulePanel` 全建 | 14/20 | 70% | 48.1–85.5% |
| Y | `ModulePanel` + patch 后台枚举 | 13/20 | 65% | 43.3–81.9% |
| **BU** | 只 `import module_panel`（模块级 `QColor` 常量 + 导入链，不建面板） | 0/20 | 0% | 0–16.1% |
| **BV** | 只建 `FlowCanvas`（自绘信号流画布） | 0/20 | 0% | 0–16.1% |

| BY | `QComboBox`×4（`addItems` + `currentIndexChanged`→lambda） | 0/20 | 0% | 0–16.1% |
| BZ | `QDoubleSpinBox`×3 + `QSlider`×3（`valueChanged`→lambda） | 0/20 | 0% | 0–16.1% |

| CB | `QFormLayout`×3 + `QLabel` 行 | 0/20 | 0% | 0–16.1% |

判据（先看区间是否重叠）：

1. **导入链 / 模块级 `QColor` 排除**：BU 0/20（≤16.1%）与 X 48.1–85.5% 不重叠
   → 触发点在**构造**，不在 import。
2. **`FlowCanvas` 排除**：只建它 0/20；把它换成桩后 BW 13/20，
   与 X 14/20 区间**完全重叠**（43.3–81.9% vs 48.1–85.5%）→ 去掉自绘不改变崩溃率。
3. **面板内 `QTimer` 不适用**：`ModulePanel` 没有自己的 `QTimer` 实例，只有
   `QTimer.singleShot(1200, ...)` 的一次性延后调用；本格 `loop=none` 从不触发它，

4. **控件类别逐一排除**：`QGroupBox` / `QComboBox` / `QDoubleSpinBox`/`QSlider` /

5. **`os._exit` 之前没有 Python 侧异常**：所有格最后标记都是 `S7_exit`，

**未定位**：单个结构都不足以复现，说明触发条件在**至少两类结构的组合**（或某个
尚未试的耦合：面板内 `setStyleSheet`、`QToolTip`/字体度量、`QLabel` 富文本、
`ModulePanel` 与 `mode_registry` 的信号回连）。继续二分需要对「组合」做组合爆炸式
采样：每个候选都要 ≥20 次独立子进程才能把 0–16% 与 65% 分开，而 57 个控件的
子集空间不是这条路能走完的。**按收口规则停止**，不再追。

**收口定性**：

- 本案**从 P0 挪走**，归为 **「开发者侧强制退出路径的已知缺陷」**
  （产品代码 0 处 `os._exit`，用户不可达）；
- 对产品可执行动作只有一条：**不要用「进程里已有 `MainWindow` 时主线程 `os._exit`」
  的写法**；测试/脚本需要硬退出时按 `tests/conftest.py` 的写法用
  `TerminateProcess`（§2.3 格 G：0/5，退出码 7）；
- 若将来某条线必须定位到具体控件，起点是 §2.8 的 BU/BV/BW 三格与 §3 的剩余清单，
  不要从 `FlowCanvas` 或枚举线程重来（两者都已排除）。

### 2.9 已否证的推测与现在成立的崩溃链（2026-11-12）

#### (a) 已否证：浮窗归位 → 布局比 Python 包装先死 → `SystemError` → 递归 → AV

**原文保留**（不改写，只标注状态）：

> `_return_panel` 注释：「不用 `deleteLater()`：`on_return` 闭包还持有 panel 的
> Python 引用，强删会让 C++ `QVBoxLayout` 比 Python 包装先走，退出时抛
> `"Internal C++ object already deleted"`。交给 GC 按引用计数收。」
>
> `closeEvent` 注释：「先收自由浮层……晚收会在窗口析构时撞上已删除的 C++ layout。」
>
> `docs/research/2026-11-11-p0-static-inference-check-rest.md` §4.5 曾据此把
> 「浮动面板的 `QVBoxLayout`」列为最可能的已删对象。

**已否证（2026-11-12；证据提交 `e34d5c56`、`88e458c8`）**，四条实测：

| # | 判据 | 探针输出 / 来源 |
| --- | --- | --- |
| 1 | `setLayout()` 内部已 `setParent(this)`，布局有父对象，不是「无父、靠 GC」 | `CPP_PARENT QWidget is_toolbar True` |
| 2 | 布局的 Python 包装由 BindingManager 缓存，不靠引用计数活 | `IDENTITY_STABLE True`、`WRAPPER_ALIVE_AFTER_GC True` |
| 3 | C++ 删除后包装正确失效，不存在「Python 还能解引用已删 C++」的窗口 | `TOOLBAR_VALID_AFTER_CPP_DELETE False`、`LAYOUT_VALID_AFTER_CPP_DELETE False` |
| 4 | `desktop/` 下 5 处 `setLayout(` 全是一次性安装，无重设/替换 → 「旧布局」构造不出来 | `grep -n "\.setLayout\(" desktop/`：ai_panel×2 / module_panel / spectrum_widget / weather_panel |
| 5 | 浮窗归位三个变体（手动归位→退出、`closeEvent` 收、强制 `panel.deleteLater()`）事件里 `isValid=False` **0 条**；布局类事件全 valid | `docs/research/…rest.md` §4.5；`docs/perf-evidence/2026-11-11/floating_return_exit_filtertrace{,_exit-return,_force-delete}.json` |

结论：注释描述的是**机制推测**，不是观测；三份追踪件里没有一条把事件钉到已删布局。
另有一条硬伤：`on_return` 闭包捕获的是 `MainWindow + key`，**不含 panel**，
所以「闭包还持有 panel」这一句本身就与代码不符（详见 B3 交接单 §4）。

#### (b) 现在成立的崩溃链（已由 `1e90b7f6` 修掉，B1/B2）

1. app 级 `MainWindow.eventFilter` 对**每个**事件无条件
   `return super().eventFilter(obj, event)`；
2. `obj` 的 C++ 对象已销毁（浮动面板归位后 `setParent(None)` 交给 GC）时，
   这一跳抛 `SystemError`（`threading.get_ident()` 也可抛同型错）；
3. 异常在事件派发里**重入**，与 `PinchZoomMixin.event` 交替递归 40+ 层，
   栈溢出，进程以 `0xC0000005` 结束。

修法（提交 `1e90b7f6`，2026-11-11 23:47）：
- `main_window.py` `eventFilter` 入口加 `shiboken6.isValid(obj)` 早退；
- 删掉唯一的抛点 `super().eventFilter(...)`，改为 `return False`；
- `touch_helpers.py:138` `PinchZoomMixin.event` 首行加 `isValid(self)`，挡住递归的另一半。
代价：8 万事件 × 一次 `isValid` ≈ 2.5–3.0 ms（构造期约 1143 ms 的 0.2%）。

**与 `ModulePanel` 70% 的关系**：两者是**独立现象**。`ModulePanel` 单建的 65–70%
崩在 `S7_exit`（主线程 `os._exit` + 已构造窗口），不经过事件派发，也从未出现
`SystemError`/递归栈；该线已在 §2.8 **阴性收口**，不得用本节 (b) 的修复去解释它，
反之亦然。
