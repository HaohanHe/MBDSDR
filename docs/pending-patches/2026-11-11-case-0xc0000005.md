# 立案：进程退出期 `0xC0000005`（CASE-2026-11-11-01）

**立案时间**：2026-11-11　**类型**：只取证，不改代码（含 `tests/conftest.py`）
**定性一句话**：这是 **PySide6 / shiboken 退出收尾期竞态**的已知家族，
不是设置线任何一笔改动引入的新回归；`tests/conftest.py` 是**规避**不是修复。

判据（2026-11-05 第二轮写死，见 `docs/limitations-register.md` 附 I）：
1. 先看退出上下文是否是**强制结束**或 `faulthandler` 转储期间；
2. 再看 WER **模块+偏移**：`pyside6+0x1c91e` / `shiboken6+0x2fe08` 属已知，出现新偏移才按新回归查；
3. 不再把「`KeyboardInterrupt` 越过 Qt 边界」当根因（PySide6 6.12 会吞掉回调内 KI）。

每次运行的机器可读判据（脚本自己打印）：

- `PLATFORM_PLUGIN offscreen` / `windows` —— 平台插件，以打印为准；
- `MAINWINDOW_ALIVE True` —— **hard 变体确实构造了 MainWindow 并 `show()`**；
- `HARD_EXIT from_thread=probe-watchdog main_thread=False` —— `os._exit(0)`
  由**看门狗 daemon 线程**调用，且发生时 `app.exec()` 仍在跑（该变体不会
  打印 `APP_EXEC_RET`）；
- bare 变体打印 `NORMAL_QUIT` → `APP_EXEC_RET 0`，走的是正常收尾。

**只陈述事实**：另一条线报「`os._exit(0)` 5/5 复现 `0xC0000005`」，与上表
的差异待按矩阵对齐（MainWindow 是否活着 / `app.exec()` 是否在跑 / 平台插件 /
`os._exit` 从哪个线程调 / 是否并发跑其它 Qt 会话）。本立案不对该结论下
「对或错」的判断。

### 2.1 原「独立进程仍崩」结论为何降级

**判断：归因不成立，待补原始复现条件。** 现有证据只支持「强制结束进程 /
`faulthandler` 转储期间会崩」这一已知家族，**不支持**「产品正常退出路径有
bug」。`conftest.py` 是规避不是修复——这点不变。

原先（`docs/research/2026-11-11-settings-convergence.md` §6，未跟踪草稿）写过
「本次复现脚本完全不走 pytest（独立进程 + 独立 profile），仍以 `0xC0000005`
退出」，但**原始脚本未留档**：路径、启动命令、退出码都拿不出来（当时的临时
探针已不在仓库、也不在 `.tmp`），没有任何文件可指认。该条因此降级为待补
（§2 表第 5 行），改用上表可复跑的对照实测。

结论修正（只记事实）：

- 正常退出路径本机 **5 次全 0**（bare 2 次 + hard offscreen 3 次），hard 在
  `windows` 平台插件下另 2 次也是 0；**不能据此说「产品退出路径有问题」**。
- 唯一有原始记录、可复现的 `0xC0000005` 仍是 2026-11-05 的**任务管理器强杀
  （11/20）与 `faulthandler` 转储期间（2/3）**，模块+偏移
  `shiboken6+0x2fe08`，属 PySide6 收尾期强拆 PySide 对象的已知家族。
- 另一条线报「`os._exit(0)` 5/5 可稳定复现」，本机同变体 5 次退出码均 0。
  **只记事实，不判对错**——差异按矩阵对齐（MainWindow 是否存活 /
  `app.exec()` 是否在跑 / 平台插件 / `os._exit` 从哪个线程调 / 是否并发
  其它 Qt 会话）。
- **未核实**：打包后的 exe 退出码 / Windows 事件日志是否也报同样异常（需在
  真实发布包上取一次退出码才能定论）。

处置：等上面「待补」补齐再决定是否动退出路径；若要动，只做「先 flush 配置 →
再终止」，不带进配置收敛。
