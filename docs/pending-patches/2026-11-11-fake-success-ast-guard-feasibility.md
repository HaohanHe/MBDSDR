# 结论：写盘/导出类「假成功」的机器守卫可行性

> 日期：2026-11-11；形态：只给判断，不落代码；适用范围：Python 桌面端
> （`desktop/*.py`）里「用户动作 → 写盘/导出 → 成功文案」这一族。

## 一、段落版结论（可直接引用）

同函数内「失败分支被吞（`except: pass` / 返回 False 但调用方忽略）→ 之后
无条件发完成态」这一类假成功，**可以用 AST 抓**；但纯语法近似（不看控制流、
只匹配 `try/except` 与末尾 `showMessage("成功")` 的共现）误报约 **40%～60%**，
加一层简单可达性判断（失败 `return`/`raise` 是否真的能到达完成态语句、
完成态是否在 `try` 之外）可压到 **15%～25%**，代价约 **200 行**解析器代码
加一份**基线抑制表**（把已确认无害的共现逐条登记，新增命中才红灯）。
**且它抓不到跨函数/状态标志型的假成功**——例如「写盘函数内部吞异常并返回
`True`，调用方据此弹成功」或「先置 `self._recording = True`，失败路径没复位、
后续按标志发完成态」。这两类仍然只能靠人工枚举与真失败路径测试发现。

## 二、能抓 / 不能抓（判据边界）

| 类型 | 例子 | AST 守卫 |
| --- | --- | --- |
| 同函数吞异常 + 无条件完成态 | `try: write() except: pass` 后接 `showMessage("已保存")` | 可抓（加可达性后误报 15%～25%） |
| 同函数「失败 return 后仍走到成功」 | `if not ok: return` 缺 `raise`，末尾统一发成功 | 可抓 |
| 跨函数：被调函数吞异常返回 True | `export_csv()` 内 `except: return True`，调用方弹成功 | **抓不到**（需跨过程值流） |
| 状态标志型 | `self._recording = True` 先置，异常分支不复位，定时器按标志写完成态 | **抓不到**（需状态机/别名分析） |
| 成功文案出现在失败路径 | `ok = write(); if not ok: logger.warning(...)` 之后同一句 `showMessage("已导出")` | 可抓（同函数可达性） |

## 三、代价与落地方式（若要做）

1. 解析器：`ast` 遍历函数体，收集「吞异常节点」集合与「完成态调用」集合
   （`showMessage` / `QLabel.setText` / 状态栏写入等），再做块级可达性判断
   （失败分支是否 `return`/`raise`、完成态是否在同一 `try` 内）。
2. 基线抑制表：`scripts/fake_success_baseline.txt` 式清单，首轮人工过一遍
   存量代码，把确认无害的共现按 `path:line+签名` 登记，之后只报新增。
3. 不做「跨函数/状态标志」的伪支持：半吊子的值流分析会产出大量不可解释的
   误报，反而让人整体关掉守卫。
4. 配套：守卫只能防回归，**不能替代**本轮这种「枚举 + 真失败路径测试」的
   人工审计；每条修复仍须有「失败分支真的会走到」的行为测试与变异反证。

## 四、给后续会话的一句话

有守卫不等于可以不做人工看：它只覆盖「同函数、能到达」的那一小撮；跨函数
返回值和状态标志型假成功必须靠逐条 action 枚举与失败注入测试。
