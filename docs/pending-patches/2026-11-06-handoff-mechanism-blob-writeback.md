## §0 硬规则（本线写死，自我约束）

> **禁止「构造 blob 写回工作区」**。提交只允许三步：
> `git hash-object -w --stdin` → `git update-index --cacheinfo 100644,<sha>,<path>` → `git commit -F <msg>`；

> 工作区永远只由正常编辑（Edit/Write 单点改动）产生，不由提交脚本产生。

## §1 事故形态（供机制线入表，编号留空）

| 项 | 内容 |
|---|---|
| 形态名（建议） | 私有索引提交前的「blob 写回工作区」覆盖 |
| 现象一句话 | 用私有 `GIT_INDEX_FILE` + `read-tree HEAD` + `hash-object` + `cacheinfo` 的**正确姿势**提交，但前置步骤把构造好的整文件内容 `write_bytes` 回磁盘，**覆盖掉别人未提交的同文件改动**；提交本身范围干净，事故不在 `git show --stat` 里。 |
| 30 秒认出法 | 提交前问一句：**「本轮提交脚本里有没有 `Write` / `write_bytes` / `> 文件`？」** 有 → 立即停；再看 `git diff --numstat <file>` 是否在本该有别人 hunk 的文件上变成 0。 |
| 触发条件 | ① 目标文件有他线未提交改动；② 为了「只提交我这块 hunk」而构造整文件 blob；③ 顺手把构造结果写回磁盘（想「让工作区与 HEAD 对齐」）。 |
| 为什么危险 | 私有索引让提交范围看起来完美（`--stat` 只有我的行），但磁盘已经被整文件替换；别人的未提交内容既不在这笔提交里、也不在任何 git 对象里，**一旦从未入库就不可恢复**。 |
| 与既有形态的区别 | 不是 §6.8「共享 index 被卷走」（那是别人把工作区整文件 `git add` 进共享索引）；本案提交索引是对的，坏在**前置写盘**。 |
| 检出命令 | `git log --all -S "<丢失段落标题>" -- <path>` 零命中 + `git diff --numstat -- <path>` 归零 + 该文件 owner 报告「我的 hunk 没了」。 |
| 正确姿势 | 构造 blob 只走管道：`git hash-object -w --stdin`；**只在私有索引里落树**，磁盘不碰。若确实要让工作区与 HEAD 对齐，必须另行征得该文件 owner 同意，且用 `git checkout -- <path>` 并先备份。 |
| 事后补救 | 立即 `git show <覆盖前最后一笔>:<path>` 或 `<覆盖前 blob>` 回写磁盘，并逐个 hunk 核对；若从未入库则只能由 owner 重放，**必须在交接里写明丢失范围**。 |
