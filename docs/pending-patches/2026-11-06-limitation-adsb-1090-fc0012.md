# 限制登记补充：本机 FC0012 收不到 1090 MHz（ADS-B 真机验收只能外部取证）

> 目标文件：`docs/limitations-register.md` · §1 待真机 · 第 L3 行（本文件**不直接改**
> 共享台账，交由限制总账 owner 合并）。
> 生成时间：2026-11-06；执行人：解码流水线 P5。
> 触发任务：查清「本机三次实采 0 帧」是硬件到不了还是采集链不对。

## 1. 实测结论（2026-11-06，本机 RTL2832U + Fitipower FC0012，SN 77771111153705700）

跑前按 `docs/hw-acceptance.md §4` 自检：SDR 相关进程**为空**，PnP `Status=OK`；
跑后同两条命令复检：进程仍为空、PnP 仍 `OK`（句柄无残留）。

逐频点单进程实测（`rtlsdr.rtlsdr.RtlSdr`，2.4 MS/s，AGC，写频后回读 + 读 32768 样本）：

| 请求频率 | 回读频率 | 结果 |
| --- | --- | --- |
| 900.000 MHz | 900.000 MHz | OK，rms -28.76 dBFS |
| 945.000 MHz | 945.000 MHz | OK，rms -27.73 dBFS |
| 948.000 MHz | 948.000 MHz | OK，rms -25.87 dBFS |
| **948.500 MHz** | **948.500 MHz** | **OK，rms -8.12 dBFS（本机实测可用上限）** |
| 948.600 MHz | — | 失败 |
| 950.000 MHz | — | 失败 |
| 1000.000 MHz | — | 失败 |
| **1090.000 MHz** | — | **失败** |

失败时回读为零、无实际调谐发生，原始报错（逐字）：

```
rtlsdr.rtlsdr.LibUSBError: <LIBUSB_ERROR_IO (-1): Input/output error> "Could not set center_freq to 1090000000 Hz"
[FC0012] no valid PLL combination found for 1090000000 Hz!
```

948.6 / 950 / 1000 MHz 的报错同构（仅频点数字不同）。

**判定：硬件物理覆盖不到 1090 MHz。** FC0012 的 PLL 组合在 948.5 MHz 之后失效，
1090 MHz 连“写频成功”都拿不到，更不存在“写进去了但收不到”的可能。
因此本机三次 1090 MHz 实采 0 帧**不是采集链参数（采样率合法性/格式/中心频偏）问题**，
是硬件上限问题；无需也未往下排查采集参数。

> 口径修正：既有台账与 `docs/real_hw_acceptance_20261103.md` 写的「上限约 948.6 MHz」
> 偏宽松——948.6 MHz 本身就已失败，实测可用上界落在 (948.5, 948.6] MHz 之间。

## 3. 证明边界（与 ADS-B any-fs 对拍同口径）

- 能证明：本机这颗 FC0012 在 1090 MHz **不可调谐**，因此本机「三次实采 0 帧」的归因是硬件上限。
- 不能证明：ADS-B 解码链本身的能力上限——那部分由 dump1090 官方 OTA 实录
  （`antirez/dump1090` `testfiles/modes1.bin`，2 MS/s u8，SHA-256 `3a33e160…3094`）对拍背书，
  **该样本不是本机录制**，只证明解调/重采样路径与外部真值一致，**不构成本机 1090 接收能力证据**。

## 5. 用户侧观察：请求 1090 时到底看到什么（2026-11-06 真实 UI 路径）

跑前按 §4 自检：无 SDR 进程、PnP `Status=OK`。用真实 `MainWindow` + 真实
`RTLSDRBackend`（offscreen，未走 mock），等价于在频率框里设 1090 MHz 再回车。
修复前（当前 HEAD 的桌面 3 个文案点尚未打补丁）实际观察：

| 观察项 | 实际值 |
| --- | --- |
| 频率主标签 `freq_label` | `1090.000 MHz`（显示“已生效”） |
| 状态栏 `status_freq` | `频率: 1090.000 MHz` |
| 状态栏消息 | `已连接 RTL-SDR #0`（**没有任何失败提示**） |
| 弹窗 | 无 |
| 日志 | 仅 `logger.warning`：`LIBUSB_ERROR_IO … Could not set center_freq`（用户看不到） |
| 设备仍连接 | `status.connected=True` |
| 后端真实回读 | `0 Hz`（硬件根本没调到 1090） |
| 保存配置 | `frequency_hz` 被写成 `1090.000 MHz` |

即：**既不是抛库异常给用户，也不是可读提示，而是静默不生效 + 状态与配置撒谎**，
命中用户列的三种可能里的第一种。

### 5.1 写频失败后句柄进入不可恢复态（必须重连）

同一进程内继续观察：1090 写频失败后，该句柄的 `center_freq` 再写一律抛
`access violation`（0xC0000005），回读恒 `0 Hz`，连 900 MHz 也写不回去；
进程退出时原生层崩溃（退出码 `-1073741819` = 0xC0000005）。**同一进程内新建
`RTLSDRBackend` 重新 `connect()` 可恢复**（实测新句柄 900 MHz 回读一致），
不需要拔插 USB，但必须换新句柄——旧句柄不可复用。

### 5.2 已落地的保护（`mbdsdr_ai/sdr_backend.py`）

1. **预检不下发**：`set_frequency` 先按 `_frequency_bounds()` 判界；
   RTLSDR 覆写为「设备声明区间 ∩ 真实 tuner 频率表 ∩ 实测上界」，
   FC0012 实测上界 `948.5 MHz`（`_MEASURED_TUNER_MAX_HZ`）。越界直接返回
   `False` + 人话，**绝不把请求写给硬件**——从源头避免触发不可恢复态。
   direct sampling 模式绕过 tuner，不套该上界。
2. **调谐器型号探测顺序修正**：改为在 pyrtlsdr 打开设备**之前**探测。
   旧顺序（先开后探）在本机恒返回 `Unknown`，导致上界协商失效；实测先探后开
   得到 `FC0012`。
3. **失败不再装成功**：`_apply_frequency` 重试耗尽返回 `False`，并置
   `_tuner_faulted=True`；后续写频直接拒绝并提示「需重新连接设备」，
   不再触达已损坏句柄。成功 `connect()` 时清故障态。
4. **失败不写 status/配置**：`set_frequency` 失败回滚 `status.frequency_hz`
   并写 `sdr_frequency_out_of_range`（越界）或 `sdr_set_frequency_failed`
   （范围内硬件拒绝）可读文案。

修复后同一 UI 探针（桌面侧补丁见
`docs/pending-patches/2026-11-06-desktop-adsb-1090-truthfulness.md`）实际观察：

| 观察项 | 修复后 |

| ADS-B 面板 | 连接后直接显示「当前设备上限 948.5 MHz，无法接收 1090 MHz；需覆盖 1090 MHz 的前端」 |
